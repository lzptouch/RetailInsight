# 设计取舍与工程决策

> 本文记录 RetailInsight 实现过程中的**判断依据**：哪些路走不通、为什么最后这么选、哪些坑是踩过之后才补的守卫。
> `README.md` 只放结论，论证过程都在这里。口径定义见 `docs/指标体系.md`，计划与评审记录见 `docs/项目编写计划.md`。
> 文中提到的上限（ARI 0.13、GBDT 增益天花板等）同时登记在 `docs/已知限制.md` —— 限制口径以那份文档为准，本文只解释成因。

## 一、三个关键取舍

面试时最值得讲的三个判断，因为它们的共性都是**先验证边界，再决定要不要硬凑**。

### 1.1 聚类：先做「先验上界检验」，再谈调参

直接拿生成器埋的真实 8 类人群当标签算轮廓系数，结果只有 **−0.056**。这个负值本身就是结论：它证明「消费体量」这一类特征在数学上**无法**分离行为型人群（促销敏感 / 周末囤货 / 季节性在 RFM 空间里本质重合），再调 K、再调参都无济于事。

所以做法改为：在多个候选特征空间里择优（`rfm3` 的 ARI 0.134 为最高），并把「哪个维度没有区分度」写进结论，而不是硬凑验收线。这里真正的产出不是一个达标的轮廓系数（0.4165 > 验收线 0.35），而是**「该特征空间的上限是多少」这个可复用的判断**。

### 1.2 流失主模型：由验收线选出，而不是由偏好选出

LightGBM 的增益 +0.0184 打不到 +0.03 验收线，RandomForest 的 +0.0305 刚好过线。于是把选型规则**写死在代码里**（`retailinsight/models/churn.py::select_main_model`：先筛「AUC ≥ 基线 + 0.03」的达标组 → 取其中 KS 最高者 → 全不达标才取 AUC 最高者），而不是事后挑一个好看的模型讲故事。这样结论可复现、可向甲方解释，换数据集也不会变成「我偏好 GBDT」。

GBDT 打不到线的原因跑了 6 组敏感性实验（`scripts/exp_churn_sensitivity.py`）才敢下结论：增益与**训练期数**正相关、与**特征维度数**负相关（12 → 31 维时 LR 基线同步变强，相对增益被摊薄）。因此 **GBDT 口径下 +0.03 是当前数据窗口下的天花板**，而不是调参没调够。

### 1.3 KS：用标准定义，不用自定义的 lift 型统计量

采用业界标准 `max|TPR − FPR|`，而不是便于讲故事的 lift 型统计量 —— 后者的上限被基线流失率锁死（本数据基线 36.7%），与「KS ≥ 0.30」这条业界验收线**不可比**。指标口径一旦自定义，验收就失去意义。

## 二、工程守卫（每一条都对应一次真实踩坑）

守卫统一放在 `tests/guards/`，跑 `make test` 即生效。

| 守卫 | 位置 | 由来 |
| --- | --- | --- |
| 依赖声明 AST 校验 | `tests/guards/test_v34_audit_fixes.py` | v3.4 发现 `plotly` / `shap` / `psutil` 从未声明、`duckdb` 被错放进可选组，新机器上 `make all` 与看板直接崩 |
| 测试不得污染产物 | `tests/guards/test_v34_audit_fixes.py` | 跑 `make test` 会把 `reports/数据质量报告.html` 覆盖成一行，导致已交付的证据被静默改写 |
| 文档数字对账 | `tests/guards/test_v36_doc_numbers.py` | 「改了生成器、忘了改文档」—— 解析 `docs/数据字典.md` 里的 mart 表行数声明，与真实 parquet 行数比对 |
| `.gitignore` 锚定仓库根 | `.gitignore` + 版本控制 | 早期未锚定（写 `/reports/` 而非 `/reports/*` 的语义差异）把**源码包** `retailinsight/reports/` 一起忽略，clone 出来的仓库直接不可运行 |
| 「幻象能力」清理 | 无（一次性删除） | 见下 2.1 |

### 2.1 能力必须有真实调用链，否则是负债

v3.5 删掉了 `scripts/download_data.py` 与 `io/schema.py::apply_mapping()` 一整套（含 `SOURCE_MAPPINGS` / `SOURCE_DTYPES` / `REQUIRED_COLUMNS` / `data/external/` 与对应测试）。

它长期被列为 ✅ 交付物，但三条证据指向同一个结论：三个数据源的 sha256 **全是 `None`**、两个源没有 url、`apply_mapping()` 的唯一消费方就是下载器本身。**没有任何真实调用链**。留着它等于给面试官一个「代码就绪」的假象；删掉后 canonical 列名由生成器直接产出，链路更短也更诚实（详见 `docs/项目编写计划.md` §0.13）。

同理，Vulture 扫出的 6 个「未使用」函数（`read_partitioned` / `CANONICAL` / `choose_k` / `fit_kmeans` / `clv_summary` / `segment_radar`）逐个核对后**一个都没删** —— 它们全部被测试或 `scripts/build_notebooks.py` 真实调用。vulture 不追踪跨文件导入，这类误报不能照单执行。

## 三、目录结构

```text
retailinsight/     # 核心包：io(schema/loader) / etl(clean/pipeline/quality/quality_html/warehouse) /
                   # features(rfm/tags/p1_tags/behavior/churn_features/cluster_features/common) /
                   # models(churn/cluster/cluster_compare/rules/clv/clv_bgnbd/segment_compare) /
                   # viz(charts) / reports(core/excel/render_decision_report/profile_cards) / cli
scripts/           # generate_synthetic.py 合成数据生成器（8 类人群 + 门店档位/人群品类乘子
                   #   + 关联埋点 + 脏数据埋点 + --members/--chunk-size 分块流式生成）
                   # fix_lightgbm_dylib.py / build_notebooks.py / exp_churn_sensitivity.py / exp_scale5.py
dashboard/         # Streamlit 4 页看板（plotly 点选下钻 + 首屏计时）
notebooks/         # 01_EDA → 02_RFM → 03_cluster → 04_rules → 05_churn（5 个，已执行）
docs/              # **人写的文档**（只放这一类）：指标体系 / 数据字典 / 项目深度讲解与面试指南
                   #   项目编写计划.md / 本文；plan/功能实现差距清单.md；images/（README 配图快照）
reports/           # **跑出来的产物**：决策建议报告 / 客群画像 / 客群方法差异论证 / 数据质量报告
                   #   (.md+.json+.html) / 性能报告 / metrics_*.json（.md+.json 入库，图与 Excel 不入）
tests/             # pytest 200 例，按域分 5 组：
                   #   etl/（清洗/仓库/分区/分块）、features/（标签/RFM）、
                   #   models/（流失/聚类/CLV/规则/防泄漏）、reporting/（报表/图表/看板）、
                   #   guards/（依赖声明、文档数字对账、历次审计缺陷回归）
```

`docs/` 与 `reports/` 的划界是硬规则：**人写的一个字都在 `docs/`，脚本跑出来的一个字都在 `reports/`**。两者混放会让人分不清「哪句话是承诺、哪句话是某次跑批的快照」。
