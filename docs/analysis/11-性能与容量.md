# 性能与容量

> 对应域：D9（工程基础 · 性能腿）。对应 Kquery 的「11-并发与容量」。压测明细见专题 `性能容量基线.md`；关键数字见 `README.md` 关键数字表。

## 〇、摘要

本项目没有「并发」问题（单机批处理），性能命题是三个：**大规模生成的内存、全链路的墙钟、规则挖掘的维度爆炸**。每个命题都有对应的工程手段与实测数字。

## 一、三个性能命题与解法

| 命题 | 解法 | 实测 |
|---|---|---|
| 大规模数据生成 OOM | 分块流式：`--chunk-size` 逐块生成 + 追加落盘，峰值内存 ≈ 单块 | 20 万会员 / 1,200 万明细 **5.2s**，峰值 ≈1.0GB，落盘 108MB |
| 明细读取放大 | 按月 hive 分区 + 窗口期只读所需分区 | 读最近 3 个月仅占全量 **20.2%** |
| FP-Growth 维度爆炸 | 数据裁剪：SKU Top300、篮长 ≤30、分门店分批 + `gc.collect()` | SKU 级 48 条 / 分门店 1,092 条稳定产出 |

辅助手段：dtype 优化（`optimize_dtypes`）压缩内存基线；全向量化 numpy 生成避免 Python 循环。

## 二、压测方法论（`scripts/exp_scale5.py`）

- **逐 stage 以子进程运行**：峰值内存互不污染（同进程连跑只会看到累积峰值）；
- 峰值 RSS 用 **psutil 轮询采样**（0.2s 间隔），比 `ru_maxrss` 更反映真实峰值；
- **压测失败也要出结论**：某 stage 爆内存时，把爆点与当时规模写进报告——这本身就是容量边界信息；
- 产物：`reports/性能报告.md`（压测规模 / 逐 stage 性能 / 产物体积 / 结论）。

## 三、容量边界（当前认知）

- scale 0.3（默认）：全链路 14 stage 约 2.5 分钟，开发迭代无感。
- scale 5：压测通过（见性能报告），明细千万行级时**分块生成是必需**而非可选。
- 未探明的边界：聚类轮廓系数抽样（`SILHOUETTE_SAMPLE`）与 SHAP 归因在百万级会员上的耗时——上量前需先补这两处采样策略。

## 四、看板性能

- 首屏 0.51s（验收 < 3s），`st.cache_data(ttl=3600)`；
- 看板数据量上限 = marts 行数（3.6 万会员级），无分页/聚合层——超出量级需重新设计。

## 五、与「高并发系统」的对照

| 维度 | 服务型系统 | 本项目 |
|---|---|---|
| 压力来源 | QPS × 尾延迟 | 数据量 × 单机内存 |
| 核心手段 | 执行器/闸门/熔断/缓存 | 分块流式/分区裁剪/向量化/dtype 优化 |
| 容量证据 | 压测 QPS 曲线 | 逐 stage 墙钟 + 峰值 RSS |

## 六、边界与已知缺口

1. 无增量计算：全量重跑的墙钟随数据线性增长，超大规模需引入增量或抽样层。
2. 峰值 RSS 轮询采样有漏峰风险（0.2s 间隔内瞬时峰值可能漏记），数量级判断不受影响。
3. 多 stage 并行未做（依赖图允许 rfm 后 cluster/rules/churn 部分并行），2.5 分钟基线下收益不 justify 复杂度。

## 维护触发

新增重计算 stage → 纳入 `exp_scale5.py` 列表；改分区/分块策略 → 重跑压测更新 `性能容量基线.md`。
