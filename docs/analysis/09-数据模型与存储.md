# 数据模型与存储

> 对应域：D7（存储与计算）。关键数字见 `README.md` 关键数字表。

## 〇、摘要

存储是**文件即数据库**的架构：parquet 三层分层 + 嵌入式 DuckDB 星型模型。DuckDB 的定位不是炫技，而是**第二实现**——用 SQL 窗口函数把 RFM 重算一遍，与 pandas 版逐行断言，自证口径正确。

## 一、三层目录（`settings.py` 统一定义）

```
data/
├── raw/        # 生成器直出（明细可按 txn_month 分区）
├── interim/    # 清洗后 + dtype 优化（明细 hive 分区：transaction_items/txn_month=YYYY-MM/）
└── marts/      # 分析集市（mart_rfm / mart_cluster / mart_churn_score /
                #   mart_basket_rules / mart_member_profile / mart_monthly / mart_quarterly）
```

纪律：所有产物路径**只引用 `settings.py` 常量**（`MART_RFM` 等），不手写文件名字面量。

## 二、parquet 与 dtype 优化（`io/loader.py`）

- 全链路 parquet（pyarrow），列式 + 压缩，较 CSV 体积与 IO 均有数量级优势。
- `optimize_dtypes`：数值列降精度（int64→int32/16、float64→float32）、低基数字符串转 category——内存与落盘双省。
- 分区：`write_partitioned` / `append_partitioned` 按 `txn_month` hive 分区；`read_items` 支持按月份窗口**只读所需分区**（读最近 3 个月仅占全量 20.2%）。
- 兼容：`ITEMS_FILE` 单文件旧产物与 `ITEMS_DIR` 分区目录双读。

## 三、DuckDB 星型模型（`etl/warehouse.py`）

```
                    dim_member
                        │
    fact_transactions ──┤
       fact_transaction_items ── dim_product
                        │            │
                   dim_store     dim_date
```

- 嵌入式文件库（`data/*.duckdb`），无服务进程；
- 聚合集市：`mart_monthly` / `mart_quarterly` 由 SQL 聚合产出，供报告趋势图使用。

### 3.1 双实现互证（本篇最重要的一节）

> 同一套 RFM 口径，pandas 算一遍（`features/rfm.py`），SQL 窗口函数再算一遍（warehouse），**逐行一致性断言**。

- 结果：35,650 行**零差异**。
- 价值：两套独立实现对得上，口径才可信；对不上，立刻定位是哪一步漂移。这是「用工程手段治理口径」而非「用评审治理口径」。

## 四、存储体量

| 产物 | 体量参考 |
|---|---|
| 分块生成落盘（20 万会员/1200 万明细） | 108MB |
| 明细分区 | 按月 1 个分区文件，窗口读取 20.2%（3 个月） |
| DuckDB 库 | 单文件，随 data/ 分发 |

## 五、一致性保障

| 机制 | 位置 |
|---|---|
| 路径常量单一真相源 | `settings.py` |
| canonical schema 常量 | `io/schema.py`（`CANONICAL`） |
| schema 测试 | `tests/etl/test_schema.py` |
| 分区读写测试 | `tests/etl/test_loader_partition.py` |
| SQL/pandas 一致性断言 | `warehouse.py`（stage 内执行） |

## 六、边界与已知缺口

1. 无并发写保护：同一产物同时跑两个 stage 会互相覆盖（CLI 顺序执行的假设下不发生）。
2. 无数据版本管理（重跑即覆盖；历史基线靠 git 管理报告与 metrics json）。
3. DuckDB 仅用于自证与即席分析，不是看板/报告的运行时依赖（它们直接读 parquet）。
