# 系统架构与运行时

> 对应域：D9（工程基础）。关键数字见 `README.md` 关键数字表。

## 〇、摘要

RetailInsight 是**单体 Python 批处理流水线 + 只读交互看板**的架构：无服务、无数据库常驻进程（DuckDB 为嵌入式文件库）、无网络接口。运行时只有两种形态——`python -m retailinsight.cli run --stage ...`（批处理）与 `streamlit run dashboard/app.py`（看板）。全部复杂性集中在三点：**stage 依赖编排、产物分层落盘、口径单一真相源**。

## 一、分层与依赖方向

```
┌─────────────────────────────────────────────┐
│ 交互层   dashboard/app.py（Streamlit，只读）  │
├─────────────────────────────────────────────┤
│ 交付层   reports/（报告渲染、Excel、画像卡片）  │
│ 可视化   viz/charts.py（13 图，matplotlib）   │
├─────────────────────────────────────────────┤
│ 建模层   models/（cluster/churn/clv/rules/…） │
│ 特征层   features/（rfm/tags/behavior/…）     │  ← 口径单一真相源
├─────────────────────────────────────────────┤
│ ETL 层   etl/（clean/pipeline/quality/warehouse）│
├─────────────────────────────────────────────┤
│ 存储层   io/（loader/schema）+ data/ 三层目录   │
├─────────────────────────────────────────────┤
│ 配置层   settings.py（路径 / 常量 / 基准日）    │
└─────────────────────────────────────────────┘
```

依赖方向**只允许向下**：看板与交付层消费 marts 产物，绝不重算指标；`features/` 是指标口径的唯一实现处（notebook、看板只调用不重算）。

## 二、stage 编排（`retailinsight/cli.py:19-26`）

- `STAGES` 共 15 个；`INTERACTIVE_STAGES = ["dashboard"]`（会占住终端），`ALL_STAGES` 实际执行 14 个。
- 执行顺序即依赖顺序：`gen → etl → rfm → cluster → rules → rules_sku → rules_store → churn → profile → warehouse → reports → report → cards → segment_compare`。
- 关键依赖边：
  - `cluster` 依赖 `mart_rfm`；
  - `profile` 依赖 `mart_rfm` + `mart_churn_score`（`cli.py:60-61`）；
  - `warehouse` 用 SQL 重算 RFM 并与 pandas 版一致性断言；
  - `report/cards/segment_compare` 依赖 profile 与各 mart。
- 每个 stage 打印 `[stage] ...` 摘要 + `[cli] stage=X elapsed=Ns`（`cli.py:219`），无独立日志框架——批处理场景 stdout 即日志。
- **无 DAG 框架**：顺序列表硬编码。规模与复杂度（14 stage、单机 2.5 分钟）不 justify 引入 Airflow/Prefect，这是刻意的取舍。

## 三、一次全链路运行的数据流

1. **gen**：`scripts/generate_synthetic.py`（子进程方式调用，`cli.py:37-43`）→ `data/raw/`（明细可按月分区落盘）。
2. **etl**：`etl/pipeline.run_etl()` → 清洗（`etl/clean.py` 逐规则函数）→ dtype 优化 → `data/interim/`（明细 hive 分区）→ 质量报告三件套。
3. **rfm / cluster / rules×3 / churn**：读 interim，写 `data/marts/mart_*.parquet` + `reports/metrics_*.json`。
4. **profile**：合并 members/txn/items/products/rfm/churn → 画像宽表；内含 CLV 双口径计算与回测指标落盘（`cli.py:83-110`）。
5. **warehouse**：建 DuckDB 星型模型，SQL 版 RFM 与 pandas 版逐行断言。
6. **reports / report / cards / segment_compare**：从 marts 回填数字 → `reports/` 全部交付物。
7. **dashboard**（单独）：只读 marts，`@st.cache_data(ttl=3600)` 缓存。

## 四、配置与单一真相源

| 真相源 | 管什么 | 反例（禁止） |
|---|---|---|
| `settings.py` 路径常量 | `MART_RFM` 等全部产物路径 | 手写 `"data/marts/mart_rfm.parquet"` 字面量 |
| `settings.py` 基准常量 | `SEED=42`、`DATA_START/END`、`COHORT_CUTOFFS`、成本系数 | 各模块自定随机种子 |
| `features/` | 指标口径（RFM、标签） | 看板/notebook 里重算 RFM |
| `io/schema.py` | canonical 列名、品类/人群/埋点常量 | 在清洗代码里散落类别名字符串 |
| `pyproject.toml` | 依赖与 pytest/ruff 配置 | 维护 requirements.txt 副本 |

## 五、失败处理策略

- **显式降级（3 处，全部留痕）**：lightgbm 缺失 → sklearn HistGB 并在 `metrics_churn.json` 的 `backend` 字段留痕；lifetimes 缺失 → 简化法 CLV 并打 `clv_method=simple_fallback` 列；shap 缺失 → permutation importance + 告警。**不允许静默产出空列**（v3.4 曾因此把 duckdb/plotly/shap 从可选依赖提升为主依赖）。
- **断言即防线**：warehouse 的 SQL/pandas 一致性、分区读写、schema 校验失败直接抛错中断 stage，不带病继续。
- **压测容错**：`exp_scale5.py` 单 stage 爆内存时把爆点与规模写进报告（容量边界信息），不让一次 OOM 毁掉整份报告。

## 六、共享状态与存储

- 无进程内共享状态：stage 间**只通过文件产物通信**（parquet / json / duckdb），天然可断点重跑任意 stage。
- 看板态共享：`st.cache_data` 进程内缓存，ttl 3600s；`RETAILINSIGHT_MARTS` 环境变量切换产物目录（测试隔离与多份数据对比的手段）。

## 七、与「服务型系统」的对照（为什么这样够了）

| 维度 | 服务型系统（如 Kquery） | 本项目 |
|---|---|---|
| 运行形态 | 常驻进程 + API | 批处理 CLI + 只读看板 |
| 并发 | 执行器/闸门/熔断 | 单进程向量化 + 分块流式 |
| 状态 | Milvus/Redis/SQLite | 文件产物 + 嵌入式 DuckDB |
| 可观测 | 探针/指标/追踪 | stdout 摘要 + metrics_*.json + 质量/性能报告 |

## 八、已知缺口（4 条）

1. 无 DAG 调度与增量计算（全量重跑；单机规模下可接受，上生产需补）。
2. 无结构化日志与运行指标落库（只有 stdout + json 指标文件）。
3. stage 间失败恢复靠人工重跑指定 stage（产物幂等覆盖，无事务）。
4. 看板无鉴权、无多用户隔离（作品集定位，单机使用）。

## 维护触发

新增 stage / 改依赖顺序 → 改 §二；新增降级路径 → 改 §五；路径常量变更 → 改 §四。
