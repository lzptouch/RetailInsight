# 第一部分 · 数据工程与性能（Q1–Q100）

## 一、架构与流水线

### Q1. 项目的整体架构形态是什么？
单体 Python 批处理流水线（14 stage 顺序执行）+ 只读 Streamlit 看板，无服务进程、无外部数据库（DuckDB 嵌入式）。stage 间只通过文件产物通信。

### Q2. 为什么 stage 间用文件产物通信而不是内存传递？
解耦与可断点重跑：任意 stage 可单独重跑（产物幂等覆盖），失败不污染上游；且产物本身可审计、可进 git 之外的分发渠道。

### Q3. 为什么不用 Airflow/Prefect 做编排？
14 个 stage、单机 2.5 分钟——硬编码顺序列表的表达力和运维成本都优于引入 DAG 框架。规模到千万级交易或需要增量调度时再引入。

### Q4. `dashboard` 为什么不进 `--stage all`？
它是交互式 stage，会占住终端直到 Ctrl+C（`INTERACTIVE_STAGES`）。`all` 必须是可无人值守跑完的批处理集合。

### Q5. CLI 的关键参数有哪些？
`--stage`（15 选 1 或 all）、`--scale`（数据规模，默认 0.3）、`--seed`（42）、`--members`（直接指定会员数）、`--chunk-size`（gen 分块）、`--port`（看板）。

### Q6. 配置管理的原则？
单一真相源：路径常量全在 `settings.py`（禁手写字面量）、口径在 `features/`、canonical schema 在 `io/schema.py`、依赖在 `pyproject.toml`、随机种子统一 `SEED=42`。

### Q7. 项目的分层结构？
配置层（settings）→ 存储层（io）→ ETL 层（etl）→ 特征层（features）→ 建模层（models）→ 交付层（reports/viz）→ 交互层（dashboard）。依赖只许向下。

### Q8. 为什么指标口径必须集中在 `features/`？
看板、notebook、报告都消费同一口径。分散实现必然漂移——这正是「SQL 双实现互证」要防的事。

### Q9. 降级机制的三条路径？
lightgbm→sklearn HistGB（`metrics_churn.json` 留 backend 字段）；lifetimes→CLV 简化法（`clv_method` 列标识）；shap→permutation importance（告警）。全部显式留痕。

### Q10. 为什么反对静默降级？
v3.4 真实教训：依赖漏声明时「不报错、只产出空列」，下游消费空数据而不自知。显式留痕让产物自描述「本次运行走了哪条路径」。

### Q11. 为什么 duckdb/plotly/shap/lifetimes 是主依赖而不是可选？
它们是主链路必经：缺 duckdb 则 `--stage all` 在 warehouse 崩、缺 plotly 看板启动即崩、缺 shap 归因静默清空。只有 lightgbm 保持可选（降级成熟且损失可接受）。

### Q12. 报告数字漂移问题怎么解决的？
渲染器模式：模板留占位符，数字从 marts 产物回填。曾发生「报告 35,576 / 实际 35,612」失配，此后数字唯一来源是代码。

### Q13. 失败处理策略？
断言即防线：schema 校验、SQL/pandas 一致性、分区读写失败直接抛错中断 stage，不带病继续；压测例外——爆内存也出报告（容量边界信息）。

### Q14. 如果让你把它改成微服务，你会吗？
不会，除非有明确的多租户/在线服务需求。当前是分析流水线，微服务只增加运维成本。正确的演进是按需加调度器与增量层。

### Q15. 项目里最有「工程感」的设计是什么？
用第二实现自证第一实现（pandas vs DuckDB SQL 的 RFM 逐行断言，35,650 行零差异）——把「口径正确」从评审问题变成工程问题。

## 二、存储与分区

### Q16. 存储介质选的是什么？为什么？
parquet 全链路：列式 + 压缩，较 CSV 体积与 IO 都有数量级优势；pyarrow 与 pandas/DuckDB 双引擎互通。

### Q17. 数据分哪三层？
`data/raw`（生成器直出）→ `data/interim`（清洗 + dtype 优化）→ `data/marts`（分析集市）。每层职责单一，产物路径由 `settings.py` 常量统一定义。

### Q18. 明细表怎么做分区？
按 `txn_month` hive 风格分区（`transaction_items/txn_month=YYYY-MM/`），`read_items` 支持月份窗口裁剪——读最近 3 个月仅占全量 20.2%。

### Q19. dtype 优化做了什么？
数值列降精度（int64→int32/16、float64→float32）、低基数字符串转 category。内存与落盘双省，百万行级明细效果显著。

### Q20. DuckDB 在项目里的角色？
不是主存储，是**第二实现**：建星型模型（2 事实表 + 4 维表），用 SQL 窗口函数重算 RFM 与 pandas 版逐行断言，自证口径；兼作即席分析入口。

### Q21. 星型模型长什么样？
`fact_transactions` 与 `fact_transaction_items` 两个事实表，挂 `dim_member / dim_product / dim_store / dim_date` 四个维表。

### Q22. 为什么旧单文件产物和新分区目录要双读兼容？
`ITEMS_FILE`（旧）与 `ITEMS_DIR`（新）并存——分区化是后引入的优化，保留兼容让历史产物可读、回归测试可对照。

### Q23. parquet 相比 CSV 在本项目的实测收益？
20 万会员/1,200 万明细分块生成落盘仅 108MB；列裁剪 + 分区裁剪让窗口分析只读 20.2% 数据。CSV 两者都做不到。

### Q24. 数据版本怎么管理？
重跑即覆盖（seed 固定 → 确定性重建）；历史基线靠 git 管理报告与 metrics json。数据本身不进 git。

### Q25. 为什么不用 PostgreSQL？
无并发写、无在线查询，单机分析负载下嵌入式 DuckDB（OLAP 向）比 PG（OLTP 向）更合适，且零运维。

### Q26. `mart_monthly` / `mart_quarterly` 是什么？
SQL 聚合产出的月度/季度集市，供趋势图与报告使用——预聚合避免每次从 217 万明细重算。

### Q27. 分区键为什么选月份？
与分析窗口天然对齐（窗口期统计、同比、cohort），且粒度适中：按日分区文件数太多，按年无法裁剪。

### Q28. 写 parquet 有什么注意点？
覆盖式幂等写（stage 可安全重跑）；分区追加用 `append_partitioned` 而非读全量再写全量。

### Q29. DuckDB 文件会进交付吗？
作为即席分析入口保留在 `data/`；报告与看板直接读 parquet，不依赖 duckdb 文件存在。

### Q30. 如果数据量到 1 亿行明细，存储方案怎么演进？
分区键细化（月→周/日）、引入 DuckDB 原生分区扫描或 Polars 流式引擎、特征层加增量计算。parquet + 分区的骨架不用换。

## 三、清洗与数据质量工程

### Q31. 清洗规则为什么每条独立成函数？
可单测 + 可对账：每条规则返回修正条数，质量报告逐条呈现「注入多少、修了多少」。

### Q32. 重复行怎么处理？
按 `txn_id` 去重保留首条，返回删除条数进质量报告（注入率 0.5% 可对账）。

### Q33. 退货的净额口径？
`net_amount = amount`（退货天然为负），金额类指标全部用净额；`is_return` 标记供频次类指标排除。

### Q34. 缺失会员的处理？
哨兵 `-1` → `member_type=非会员`，保留交易（散客 GMV 是真实收入），会员专属分析过滤。

### Q35. 缺失判定为什么要区分类型？
整数 ID 列判 `isna | ==-1`（哨兵）；字符串列 strip+lower 后比对哨兵集合（"未知"/"未填"/"null" 等）；其余判 isna。业务口径的缺失 ≠ NaN。

### Q36. 逻辑异常怎么定义？
生成器注入的冲突数据（如时间乱序 1,511 行），统一打 `is_logic_error=True`，分析侧剔除但不从数据里删除——剔除行为本身要可审计。

### Q37. 品类别名问题怎么修？
`CATEGORY_ALIASES` 映射表归一（如别名→canonical 品类），返回修正条数。注入率 2% 可对账。

### Q38. 质量报告为什么三种格式？
md 人读、json 程序读（测试可断言）、自包含 HTML 可分发（无依赖双击即开）。

### Q39. 清洗为什么不直接 drop 异常行而是打标？
可审计 + 灵活：不同分析对异常的容忍度不同（GMV 口径剔逻辑异常、质量分析本身要看异常），打标把决定权留给下游。

### Q40. ETL 的输出约定？
interim 层 parquet（dtype 优化后）+ 明细分区 + 质量报告三件套，一次 `run_etl()` 全部产出。

### Q41. 怎么保证清洗规则不被悄悄绕过？
质量报告 json 可被测试断言；`tests/etl/` 6 个文件覆盖每条规则；清洗前后行数差必须等于规则修正数之和。

### Q42. 真实项目里脏数据还有什么本项目没覆盖的？
价格离群、负数库存、跨表外键悬空、时区混乱。项目报告只呈现不自动处理未覆盖类型——这是已登记的缺口。

### Q43. 为什么清洗放 ETL 而不是生成器直接产干净数据？
故意注入脏数据就是为了演练清洗链路——「数据干净」是结论不是假设。

### Q44. 数据质量的核心指标？
行数对账（raw vs interim）、各规则修正条数、缺失率（业务口径）、逻辑异常占比。

### Q45. 质量门禁会不会阻断流水线？
当前质量报告是「呈现」而非「阻断」——分析报告型项目的合理选择；上生产可加阈值阻断（如缺失率超限 fail stage）。

## 四、特征工程

### Q46. RFM 特征在哪计算？
`features/rfm.py` 唯一实现；基准日=最大交易日+1，R/F/M 口径见 100 题 Q21。

### Q47. 画像标签分几组？
P0 20 个（基础属性/消费能力/行为偏好/生命周期 各 5）+ P1 18 个扩展 + CLV 4 列。

### Q48. 时段特征怎么做？
`HOUR_BANDS` 四段（凌晨/上午/下午/晚间），会员主时段带作为行为标签；高峰 10/9/11 点是全店口径。

### Q49. 品类熵的计算与用途？
信息熵 `-Σp·log2p` 衡量购买品类分散度，区分专一型/逛店型，指导推荐策略。

### Q50. 流失模型的特征方向？
RFM 基础 + 趋势类（频次/客单价的近远窗口对比）+ 行为结构（品类集中度、折扣敏感度、间隔分布）。趋势类比静态值预测力强。

### Q51. 聚类特征为什么要 log1p？
消费金额/频次强右偏，log1p 压缩长尾让 K-Means 的距离度量不被极端值主导；之后再 StandardScaler。

### Q52. 聚类特征空间怎么选？
多候选空间按「与先验人群的 ARI」择优、轮廓系数护栏，全部评估落盘 `metrics_cluster.json` 可审计。

### Q53. 特征泄漏在流失模型怎么防？
特征只用观察窗（270 天）、标签只看标签窗（90 天），物理隔离 + 三向时间切分 + 探针测试。

### Q54. CLV 特征是什么？
BG/NBD 只需要 (frequency, recency, T) 三元组 + Gamma-Gamma 需要客单价均值——这是它工程友好的原因。

### Q55. 行为偏好类标签有哪些？
偏好品类、偏好品牌、时段带、周末占比、品类熵；P1 加深到复购间隔、品类迁移、价格带偏好。

### Q56. 折扣敏感度怎么算？
`features/behavior.py: discount_sensitivity`，折扣单占比口径；用于画像和流失特征两侧。

### Q57. 特征层为什么不直接用 SQL 全部实现？
pandas 表达复杂行为特征更灵活；但 RFM 这类核心口径用 SQL 实现了第二遍做互证——灵活与自证各取一处。

### Q58. 新加一个标签的正确流程？
`features/` 实现 → 单测 → 进画像宽表 → 评估是否影响画像卡片规则表与看板 → 更新文档。

## 五、内存与性能

### Q59. 大规模生成的内存怎么控制？
`--chunk-size` 分块：逐块生成 + 分区追加落盘，峰值内存 ≈ 单块。20 万会员/1,200 万明细实测峰值 ≈1.0GB。

### Q60. 分块生成快吗？
5.2 秒（20 万会员/1,200 万明细）。全向量化 numpy，无 Python 级循环。

### Q61. `chunk_size=0` 的意义？
兼容路径：产物与历史基线字节级一致——分块是可选优化，不改变默认行为，有测试守卫。

### Q62. 规则挖掘的内存三招？
品类级 60 维直接跑；SKU 级先裁 Top300 + 篮长 ≤30；分门店按 store_id 分批 + 批间 `gc.collect()`。

### Q63. 为什么 SKU 级必须「先裁再挖」？
5,000 维 one-hot 矩阵内存必然爆。裁到 300 维后稀疏矩阵可承受——控制问题规模比优化算法更优先。

### Q64. 压测怎么做的？
`scripts/exp_scale5.py`：逐 stage **子进程**运行（峰值内存互不污染），psutil 0.2s 轮询采样峰值 RSS，产出性能报告。

### Q65. 为什么用子进程逐 stage 压测？
同一进程连跑各 stage 只会看到累积峰值，无法归因；子进程让每个 stage 的峰值独立真实。

### Q66. 为什么用轮询采样而不是 `ru_maxrss`？
`ru_maxrss` 是进程生命周期最大值（含子进程聚合语义问题），轮询采样更反映时间线上的真实峰值；0.2s 间隔的漏峰风险在数量级判断上可接受。

### Q67. 压测失败怎么办？
「失败也要出结论」：爆内存的 stage 与当时规模写进报告——容量边界本身就是交付物。

### Q68. 看板首屏怎么做到 0.51s 的？
`@st.cache_data(ttl=3600)` 缓存 parquet 读取 + marts 预聚合（看板不重算）。验收线 <3s。

### Q69. 首屏计时口径是什么？
Streamlit 每次交互重跑脚本，口径取「脚本开始到首屏渲染完成」；缓存命中时显著变小——0.51s 是命中口径，已注明。

### Q70. 全链路 2.5 分钟怎么分布的？
明细逐 stage 墙钟见 `reports/性能报告.md`；大头在规则挖掘与 churn 特征构建（明细行级操作）。

### Q71. 有哪些已知的性能未探明区？
聚类轮廓系数抽样与 SHAP 归因在百万级会员上的耗时——上量前需先补采样策略（已登记缺口）。

### Q72. 多 stage 并行为何不做的？
rfm 之后 cluster/rules/churn 理论上可并行，但 2.5 分钟基线下收益不 justify 复杂度。要做也是调度层的事，不改 stage 本身。

## 六、测试与质量门禁

### Q73. 测试规模？
24 个文件、200 用例、覆盖率 82.78%，ruff 全绿。

### Q74. 测试目录怎么组织？
`tests/etl/`（6）+ `tests/features/`（2）+ `tests/models/`（7）+ `tests/reporting/`（4）+ `tests/guards/`（5）。

### Q75. 守卫测试是什么？
每次重大修复沉淀一个防回归文件：v32 特征、v33/v34 审计修复、v36 文档数字一致性 + import 冒烟。**修过的缺陷永不复活**。

### Q76. import 冒烟测试防什么？
依赖漏声明——v3.4 的真实缺陷（duckdb/plotly/shap 漏声明）。全模块 import 一遍，漏声明立刻现形。

### Q77. 防泄漏测试怎么设计？
构造「含标签窗信息的探针特征」——如果隔离失效，AUC 会异常高。测的不是模型准，而是**模型不可能作弊**。

### Q78. 看板怎么测？
Streamlit 官方 AppTest：起真实脚本、模拟交互、断言渲染与筛选联动；`RETAILINSIGHT_MARTS` 指向夹具产物隔离真实数据。

### Q79. 覆盖率门禁为什么不在 addopts？
addopts 会让 `pytest tests/单文件.py` 因「总覆盖率 0%」必红（v3.6 修）。门禁 `--cov-fail-under=60` 只在 `make test`/`make cov` 全量生效。

### Q80. 为什么门禁 60% 而实际 82.78%？
门禁是下限不是目标——留出演进空间避免「为覆盖率写测试」；实际水平远高于门禁说明测试文化是真实的。

### Q81. ruff 门禁的规则集？
E/F/I/UP/B/SIM，line-length 110，忽略 E501。`make lint` 必须全绿。

### Q82. 为什么 `ruff format` 不进门禁？
仓库尚未统一格式化（50/56 文件会被重排），进门禁会长期红灯；作为建议项单独 `make format`。

### Q83. 测试之外还有哪些验证资产？
先验人群 ARI、埋点回收率 4/4、SQL 双实现零差异、时间外回测 ×2、神谕上界、6 组敏感性实验——超越单测的方法论验证。

### Q84. 测试缺口有哪些？

### Q85. 数字一致性怎么保证？
`test_v36_doc_numbers.py` 守卫文档/报告数字与产物一致；报告渲染器从机制上消灭手写漂移。

### Q86. CI 情况？
当前以 Makefile 为门禁入口（test/lint/cov），无托管 CI workflow——作品集规模下的取舍，上 GitHub 可直接映射为 workflow job。

## 七、复现与环境

### Q87. 从零复现的步骤？
venv → `make install` →（macOS 必要时 `fix_lightgbm_dylib.py`）→ `make all` → `make test` → `make dashboard`。全部命令在根 README。

`RETAILINSIGHT_MARTS=/path/to/other/marts` 重定向看板数据源，不动仓库内产物。

### Q92. 重置环境怎么做？
`make clean`（缓存）+ 删 `data/`、`reports/` 后 `make all` 重建。

### Q93. 依赖管理双通道？
`pip install -e ".[dev]"` 与 `uv sync`（uv.lock）并存；锁文件 freshness 手工维护，已登记为缺口。

### Q94. 可选依赖的哲学？
只有「降级路径成熟且指标损失可接受」的才可选（lightgbm）；主链路必经的一律主依赖（v3.4 教训）。

### Q95. Notebook 怎么保证不过期？
`scripts/build_notebooks.py` 从库代码构建 5 个 notebook 并执行保存输出；指标只调 `features/` 不重算，库改则 notebook 重建。

### Q96. 没有 Docker 是缺陷吗？
对作品集不是：复现路径 5 条命令以内、依赖纯 Python 生态。上生产再容器化，Dockerfile 映射 Makefile 即可。

### Q97. 环境变量有几个？
只看板用 `RETAILINSIGHT_MARTS`（产物目录重定向）。批处理全部参数化走 CLI，不依赖环境变量——可复现性优先。

### Q98. 新同事第一天跑不起来，最可能的原因？
按概率：① 没 `make install` 直接跑（缺依赖）；② macOS lightgbm libomp（有自动降级，只是指标略低）；③ 先跑下游 stage 没跑 gen/etl（产物不存在）。

### Q99. 报告和代码的版本对应关系？
报告由代码渲染生成，重跑即同步；metrics json 与报告同批产出。历史版本靠 git 追溯。

### Q100. 如果要加一个 CI workflow，放哪几个 job？
lint（ruff）→ test + 覆盖率门禁 → `make all` 全链路冒烟（scale 缩小）→ 文档数字守卫。直接映射现有 Makefile 目标。

# 第二部分 · 项目交付与面试表达（Q101–Q200）

## 八、报表与看板工程

### Q101. 决策报告怎么生成的？
模板（`决策建议报告.md.tpl`）+ 渲染器从 marts 回填全部数字 → `reports/决策建议报告.md`。数字唯一来源是代码。

### Q102. 为什么报告要做成渲染器？
手写数字会漂移（实测失配案例：35,576 vs 35,612）。渲染器让「报告永远等于最新一次运行」。

### Q103. 报告结构？
执行摘要 → 关键发现 → S1~S8 建议（每条：测算公式+假设+验证方式）→ 落地路线图 → 方法附注。

### Q104. 画像卡片内容？
8 客群各一页：规模/GMV 贡献/消费能力/偏好品类品牌/流失与 CLV/触达建议。建议由规则表驱动，不写死文案。

### Q105. Excel 报表有什么？
6 个 sheet 的核心报表矩阵（`build_core_reports()`），纯数据 sheet，图表以 png 单独分发。

### Q106. 13 张图都有哪些？
GMV 趋势、客群分布、客群价值、lift 曲线、流失概率直方图、规则网络、品类帕累托、时段热力等，`viz/charts.py` 统一产出。

### Q107. 看板 4 页分别是什么？
经营驾驶舱 / 客群分析 / 商品洞察 / 流失预警。数据源只读 marts，不重算指标。

### Q108. 看板最强的交互？
plotly 散点（R×M，气泡=频次）点选下钻：点击任意会员 → 右侧完整画像 + 同客群对比。把统计结论变成可逐个查看的具体人。

### Q109. 看板为什么不做写回/配置？
防止「看板一套口径、报告一套口径」——口径变更必须改 `features/` 重跑，看板只读是刻意的。

### Q110. `load_optional` 解决什么？
可选产物不存在时返回 None 而非崩溃——只跑到 rfm 也能开看板看两页，开发与演示体验都更好。

### Q111. 看板缓存策略？
`@st.cache_data(ttl=3600)`；重跑流水线后需手动清缓存或等过期——无产物指纹失效机制，已登记缺口。

### Q112. 图表为什么用 matplotlib 而不是 plotly 出静态图？
静态交付场景（报告/README/打印）matplotlib 更稳、无 JS 依赖；交互场景才用 plotly（看板）。各取所长。

### Q113. 规则网络图为什么不引 networkx？
确定性圆周布局自绘：少一个重依赖 + 每次渲染一致（可进回归测试）。

### Q114. 数据质量报告的 HTML 为什么强调「自包含」？
可分发性：单文件双击即开，不依赖仓库环境——给非技术干系人交付的关键属性。

### Q115. 交付物里哪件最能打动业务方？
决策建议报告 S1~S8：每条建议都有「测算公式+假设+验证方式」，不是观点是可复核的算式。

## 九、决策建议深挖

### Q116. S2 流失挽回的测算逻辑？
高危 5,014 人 × 挽回率假设 × 人均年净消费 × 毛利率 30% = 收益区间；成本 = 触达券成本。成本比（漏判 1 = 误触 8）与模型阈值同口径。

### Q117. S5/S6 与关联规则的关系？
S5 捆绑采购引用 洗发水→护发素（lift 8.30）；S6 关联陈列引用 火锅底料→牛羊肉（lift 5.02）。规则 lift 是测算的输入参数。

### Q118. S8 门店差异化的证据与局限？
1,092 条分门店规则 + 品类差异度 0.0502；局限：合成数据差异度在真实区间下沿，方向可信、量级保守——已标注。

### Q119. 头部客群建议为什么是「防打扰」？
重要价值客户已在高频高消费，过度促销只损失利润不带来增量；权益与专属服务维持忠诚度即可。

### Q120. 可运营池 15,494 人的建议逻辑？
他们已有复购（证明意愿）但未达高频——从 39.2% 转化率往上抬的边际收益最高的池子，配频次权益类动作。

### Q121. 品类集中 63.1% 的采购建议？
Top5 品类加深谈判与库存深度；A 类 6 品类重点保供；长尾 54 品类结构精简 SKU 宽度。

### Q122. 建议里的假设怎么处理不确定性？
区间测算 + 敏感性标注（如挽回率给区间不给点值），假设全部显式列出可复核。

### Q123. 落地路线图怎么排？
按「数据就绪度 × 预期收益」排序：不需要新数据的（头部维护、陈列调整）先行，需要新标签/新链路的排后。

### Q124. 为什么建议必须有「验证方式」列？
让每条建议在执行后可复盘：哪个指标、哪份产物、多少算成功。没有验证方式的建议只是愿望。

### Q125. 如果业务方质疑 GMV 口径？
净额口径（实付−退货），退货单不参与 F 但参与 M——口径定义在 `features/rfm.py` 头注释与指标文档，SQL 双实现可现场对账。

### Q126. 高风险客群 37.8% 却只说 5,014 人挽回，矛盾吗？
不矛盾：37.8% 是 RFM 规则口径（含低价值沉睡者，挽回 ROI 差）；5,014 是模型高危 × 价值过滤后的可行动名单。两个口径服务两个问题。

### Q127. 季节双峰（12.8 倍）怎么用？
峰值月 2021-12（315.4 万）vs 淡季 24.7 万——备货与人力按峰值排程，营销预算向峰值前一个月倾斜。

### Q128. 建议与模型的对应关系会漂移吗？
不会：报告回填机制保证建议引用的数字与当次运行一致；S 编号与模型的对应写死在模板结构里。

### Q129. 哪条建议最依赖 CLV？
挽回优先级排序：高危名单 × CLV 分层取交集——高流失风险但低 CLV 的不值得挽回预算。

### Q130. 如果只能落地一条建议？
S2 流失挽回：目标人群明确（5,014）、动作直接（定向券+回访）、收益可测算、验证闭环短（30 天回访核销）。

## 十、方法论与取舍

### Q131. 项目最重要的方法论？
先定验收线再动手；每个主模型配对照组；未达标如实报告。三条贯穿全部建模决策。

### Q132. 为什么不追求更高 AUC？
+0.03 验收线已达到；继续刷指标的边际收益低于把结果转化为决策建议。项目目标是「可用」不是「最高」。

### Q133. 合成数据最大的质疑怎么回应？
「结论全是编的」——回应：① 结论可验证性反而更强（埋点真值）；② 所有外推局限如实标注；③ 方法论（防泄漏/回测/双实现）与数据真假无关，真实数据上照样成立。

### Q134. 为什么阈值用业务成本而不是统计准则？
阈值是决策：运营预算约束下，漏判与误触的代价不对称（1:8）。统计准则（Youden）假设对称，会系统性选错切点。

### Q135. 为什么评估用时间切分不用交叉验证？
时序数据违反 CV 的 i.i.d. 假设，分数系统性偏乐观；三向时间切分模拟「用过去预测未来」的真实使用。

### Q136. 双实现互证的成本收益？
成本：RFM 写两遍。收益：35,650 行零差异的口径可信度——所有下游结论的地基。值。

### Q137. 为什么报告回填而不是「跑完手工更新」？
手工更新必然漂移（有实测失配案例）；机制保证比纪律保证可靠。

### Q138. 降级为什么不直接报错？
分析链路的可用性优先：没有 lightgbm 的环境（如部分 CI/新同事机器）也应能跑完全程，只是指标略低且留痕。

### Q139. 什么时候选择报错而不是降级？
口径正确性受影响时（如 schema 不符、SQL/pandas 不一致）——宁可中断也不产出错误结论。

### Q140. 为什么轮廓系数验收线定 0.35？
事前定的合理线（神谕上界证明在该特征空间可达且有余量），既不过松（0.2 的碎群也能过）也不过苛（0.5 在重叠人群上不可达）。

### Q141. 为什么主口径 RFM 而不是聚类？
业务可读性：RFM 客群有成熟动作库；聚类做交叉验证捕捉非线性结构。差异论证报告支持这个分工。

### Q142. 项目里最大的妥协？
全量重跑无增量——2.5 分钟基线下的合理妥协，上量后是第一个要还的技术债。

### Q143. 为什么没有概率校准？
churn_prob 用于排序与分层（lift/阈值），不直接当概率用——校准是「上生产做预算精算」时的下一步，已登记。

### Q144. 怎么看待「模型简单」的质疑？
LR/RF/K-Means 都是成熟方法——分析项目的价值在「问题定义 + 验证严谨 + 决策转化」，不在模型新奇度。敏感性实验证明瓶颈在数据窗口而非模型容量。

### Q145. 为什么测试要包含文档数字守卫？
文档也是交付物，文档数字错了和代码 bug 同罪——`test_v36_doc_numbers.py` 把文档纳入测试面。

### Q146. 项目的「诚实」体现在哪？
LightGBM 未达标写入报告；合成数据局限标注；首屏 0.51s 注明缓存命中口径；CLV「只在合成数据验证过」写入模块文档。

### Q147. 如何向技术面试官证明不是「教程缝合」？
讲三个反教程的设计：埋点验证、双实现互证、成本阈值——教程里没有对照组文化。

### Q148. 为什么 Notebook 由脚本构建？
保证 notebook 与库代码同源，库改则 notebook 重建——防止「notebook 里的旧代码」这个经典腐败源。

### Q149. 项目里你最想删掉的东西？
（诚实回答示例）`ITEMS_FILE` 单文件兼容路径——历史包袱，等确认无旧产物消费方后应删除。

### Q150. 方法论上还想补什么？
因果推断（当前建议是相关性驱动，A/B 验证框架未建）； uplift 模型做挽回人群精选。已列入演进方向。

## 十一、项目讲述与 STAR

### Q151. 60 秒电梯陈述？
「做了一个连锁商超会员分析系统：从合成数据到决策建议全链路，RFM+聚类+流失+关联规则+CLV 五个模型，每个都有对照组和验收线；最强结果是流失模型 Top20% 名单捕获 46.77% 真实流失者；8 条业务建议全部带量化测算。200 测试、82.78% 覆盖率。」

### Q152. STAR 讲流失模型？

### Q153. STAR 讲性能优化？
S：scale 5 压测需求。T：生成 20 万会员/1,200 万明细不爆内存。A：分块流式 + 分区追加 + 全向量化。R：5.2s、峰值 1.0GB、落盘 108MB。

S：脏数据会影响所有结论。T：清洗可验收。A：生成器按已知比例注入 5 类脏数据 + 逐规则清洗 + 三格式质量报告；修缺失哨兵判定的真 bug。R：清洗 315,139→313,571 笔，全部对账。

### Q157. 怎么讲项目的业务价值？
不讲模型讲决策：8 条建议每条有钱（测算），最强的三个数字——18.3% 人贡献 42.5% GMV、5,014 人挽回名单、Top5 品类 63.1% 集中度。

验证资产密度：埋点、双实现、回测、守卫测试——大多数作品集只有「跑了模型」，这个项目证明了「模型是对的」。

### Q170. 结束语怎么说？
「这个项目的方法论——验收线前置、对照组必备、未达标如实报告——是我在真实工作里也会坚持的。」

## 十二、高频追问与压力面

### Q171. AUC 0.83 不算高，怎么说？
时间外推下的真实水平：随机切分能刷到 0.9+ 但上线即崩。Top20% lift 2.34（上限 86%）说明排序能力接近数据允许的天花板。

### Q172. 轮廓系数 0.42 不高吧？
对照神谕上界：埋点人群在该特征空间本就只有 ARI≈0.13 的可分性，0.4165 接近天花板。绝对值不如「相对天花板的位置」重要。

### Q173. 为什么不用深度学习？
表格数据 + 3.6 万样本：GBDT/RF 是该规模的 SOTA 区间；且可解释性（SHAP/系数）是业务交付的硬需求。深度模型在这个规模没有收益证据。

### Q174. 你的 CLV 不就是套 lifetimes 库吗？
库只提供拟合器；口径设计（91 天时间外回测、与简化法同台比较、偏差分析）是本项目的方法论——而且回测证明了换口径的价值（MAE 降 15.3%、偏差从 +74 压到 −1.4）。

### Q175. 合成数据项目能算真实经验吗？
工程能力（流水线/测试/性能）与方法论（防泄漏/回测/口径治理）完全真实；业务直觉部分如实承认需要真实数据历练——这正是标注所有局限的原因。

### Q176. 如果真实数据的结论和合成数据相反呢？
正常且预期内——所以所有参数设计为可重估、所有回测是链路的一部分而非一次性结论。流水线不变，结论重算。

### Q177. 200 个测试是不是凑数？
看构成：7 个模型测试含防泄漏探针、4 个报告测试含看板 AppTest 端到端、5 个守卫测试各对应一次真实修复——没有为覆盖率写的凑数测试。

### Q178. 毛利率拍脑袋 30%？
标注为假设值（行业 25%~35% 区间中值）；所有含毛利率的测算给出公式，替换参数即可重算。分析项目里假设显式化比假装精确重要。

### Q179. 为什么没有实时/在线部分？
业务问题（月度运营与采购决策）不需要实时；看板 + 定期重跑匹配决策节奏。为实时而实时是过度工程。

### Q180. 你一个人做的，怎么保证没抄？
讲演进史：v3.2→v3.7 每轮修复有守卫测试与文档记录（依赖漏声明、缺失哨兵、覆盖率门禁位置……），抄来的项目没有这种「伤疤史」。

### Q181. 为什么 RF 主口径而 LightGBM 名气更大不用？
按验收线选模型不按名气：RF +0.0305 达标、LGBM +0.0184 未达标（敏感性实验证明是窗口天花板）。结果是证据不是偏好。

### Q182. Top20% lift 2.34 怎么算的？
测试集按 churn_prob 降序取前 20%，其中真实流失者占比 / 全体流失率 = 2.34；该名单捕获 46.77% 的流失者，上限（流失率 20%→完美排序 lift 5）折算后达理论上限的 86%。

### Q183. 压测只跑 scale 5 够吗？
对「作品集 + 单机」定位够：证明了分块机制有效且边界已知。真正的容量规划需要生产环境数据量级输入——方法论（子进程隔离 + 峰值采样 + 失败出结论）是通用的。

### Q184. 如果你错了怎么办？（开放压力题）
每类结论都有「推翻路径」：回测重跑、对照组重估、埋点重验——项目设计上就允许被证伪，这比「保证正确」更可信。

### Q185. 这个项目对你下一份工作的价值？
可直接迁移的：时序建模防泄漏、口径治理（双实现/回填/守卫）、分析报告工程化、性能分块模式。需重新积累的：真实数据的脏与偏、跨团队协作、生产监控。

## 十三、业务理解与行业常识

### Q186. 商超会员运营的核心杠杆？
复购频次与客单价；本项目漏斗显示最大空间在「复购→高频」（39.2%）一档。

### Q187. RFM 在零售业的地位？
最经典的客户分层框架：简单、可解释、动作库成熟——缺点是静态截面，本项目用聚类与流失模型补动态维度。

### Q188. 流失挽回的经济学？
挽回成本 < 客户剩余价值（CLV）× 挽回率才值得做——所以高危名单要 × CLV 分层取交集。

### Q189. 关联规则在零售的经典案例？
「啤酒与尿布」传说（真实性存疑）；本项目的 洗发水→护发素（8.30）、火锅底料→牛羊肉（5.02）是更可信的现代版本。

### Q190. ABC 分析怎么用？
A 类（6/60 品类）重点保供与谈判深度，C 类精简 SKU——库存资金向头部集中。

### Q191. 为什么周末占比 29.7% 值得关注？
2/7≈28.6% 是均匀基准，29.7% 仅略高——说明该店非典型周末型商超，排班不必极端向周末倾斜。不显著的结论也是结论。

### Q192. GMV 季节双峰（12.8 倍）的行业解释？
12 月（年货/节庆）+ 年中档——商超典型节律；供应链与人力按峰值排程是基本功。

### Q193. 品类管理（Category Management）是什么？
以品类为经营单元的零售管理方法论：角色定位（目的性/常规性/季节性/便利性品类）→ 策略 → 执行。本项目 Top5 集中度与规则产出是它的数据输入。

### Q194. 会员制商超与非会员制的分析差异？
会员制有全量消费轨迹（可做 RFM/CLV）；非会员只有交易流水（只能做购物篮与时段分析）。本项目 3% 非会员交易的处理体现了这个差异。

### Q195. 零售毛利率为什么 25%~35%？
商超业态的行业区间（生鲜偏低、自有品牌偏高）——取 30% 中值作假设，真实企业用财务实际值。

### Q196. 如果让你分析一家便利店而不是商超，改什么？
窗口缩短（便利店购买周期更短）、时段粒度加细（早高峰是主战场）、SKU 级规则权重提高（单品决策占比大）、RFM 的 F 阈值按周重新定义。

### Q197. 线上电商与线下商超的分析差异？
电商有浏览/加购行为漏斗，线下只有成交；线下购物篮是物理同单（关联规则更真实），线上「一起买」可能跨天。

### Q198. 怎么向门店经理解释 lift？
「买洗发水的顾客，买护发素的概率是普通顾客的 8.3 倍——所以这两样要摆在一起」。

### Q199. 数据分析师在零售企业的价值定位？
把「经验决策」变「算账决策」：每条建议有公式、有假设、可复盘——本项目的 S1~S8 就是这个定位的样板。

### Q200. 最后：这个项目一句话的卖点？
**「我不只会跑模型——我能证明模型是对的，并且算得出它值多少钱。」**
