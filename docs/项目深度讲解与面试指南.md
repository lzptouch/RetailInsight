## 一、项目全景

### 1.1 一句话定位

RetailInsight 模拟一家零售数据服务公司（乙方）为连锁商超「悦鲜生活超市」（甲方）提供的**会员画像分析服务**：用 31 个月（2020-01 ~ 2022-07）交易数据回答「谁是重要客户、谁在流失、商品怎么搭配采购」，最终交付可执行的会员运营与采购策略建议。

### 1.2 业务问题 → 分析方法 → 产出物 的映射

| 业务问题 | 方法 | 产出物 |
|---|---|---|
| 谁是高价值/潜力/流失风险会员？ | RFM 五分位打分 + 8 类客群规则 | `mart_rfm`、客群画像卡片 |
| 各客群消费偏好？ | 画像标签体系（P0 20 个标签） | `mart_member_profile` |
| 谁未来 90 天会流失？ | 流失预测（LR 基线 + LightGBM） | `mart_churn_score`、高危名单 |
| 哪些商品一起卖？ | FP-Growth 关联规则 | `mart_basket_rules`（品类级 177 条）、`mart_basket_rules_sku`（48 条）、`mart_basket_rules_store`（1,092 条） |
| 品类结构健康吗？ | ABC / 帕累托分析 | Excel 报表 sheet 4 |
| 销售高峰在何时？ | 星期×小时热力图 | 图 04 |
| 结论如何变成动作？ | 决策建议报告（8 条建议含测算） | `docs/决策建议报告.md` |

### 1.4 核心结果速览（scale=0.3：3.6 万注册会员 / 31.4 万交易 / 217 万明细，有效窗口 2020-01 ~ 2022-07）

|---|---|

## 二、技术要点详解

### 2.1 合成数据生成器：让数据「有故事可讲」

开源数据集（Dunnhumby、Online Retail II）是真实分布，但讲不了「中国商超」的业务故事。本项目选择**以合成数据为主、开源数据为可插拔验证源**的方案，生成器是技术密度最高的模块之一：

**① 8 类隐式人群埋点**（`io/schema.py::PERSONAS`）
每类人群有独立的行为参数：年消费频次、单次件数、客单价系数、周末权重、折扣敏感概率、生命周期形态（stable/new/seasonal/churn/once）。例如「周末囤货」人群周末权重 2.5、单次件数 14；「沉默流失」人群活跃期中途截断且临近流失点频次按 \(u^{1.6}\) 衰减（制造可学习的「消费变稀」信号）。

**价值**：模型上线后无法验证聚类对错，但合成数据可以先验对照——聚类结果与 8 类先验人群做列联表，能量化「聚类找回了多少真实结构」。

**② 4 组购物篮关联埋点**：啤酒+纸尿裤、火锅底料+牛羊肉、面包糕点+乳制品、洗发水+护发素，以 5%~8% 概率注入交易前两件。关联规则模块若能回收全部 4 组，即证明挖掘链路有效——本项目 4 组全部回收。

**③ 4 类脏数据埋点**：重复行 0.5%、会员ID 缺失 3%（哨兵 -1）、负金额退货 1%、品类别名 2%（`清洁用品`/`清洁 用品`）、时间戳逻辑冲突 0.5%。脏数据是刻意设计的，否则数据清洗环节无米下锅、面试无坑可讲。

**④ 全向量化生成**：不用 for 循环逐行造数据。会员级用 `np.random.poisson` 生成频次、`np.repeat` 展开成交易、逆 CDF 采样（`searchsorted`）处理周末加权的天分布与双峰小时分布。12 万会员 / 130 万交易（scale=1）秒级完成。

### 2.2 ETL 与数据质量

**清洗规则的取舍体现业务理解**：
- 会员ID 缺失的交易**不删除**，归入「非会员」客群单独分析——删除会低估 GMV、且丢掉了非会员转化率这个业务指标；
- 负金额退货**不删除**，打 `is_return` 标记单列分析——退货率是画像标签之一；
- 金额极端值按 P99.9 截断并**记录剔除率**（验收 ≤3%），而不是静默删除。

**dtype 与存储优化**：ID 列 int64→int32、金额 float64→float32、低基数字符串→category，整体内存降 60%+；全链路落 parquet（列存+压缩），明细表可按月分区只加载窗口期。

### 2.3 RFM 与口径纪律

**RFM 口径**（写入 `docs/指标体系.md`）：
- R = 基准日 − 最近消费日，基准日 = 数据最大交易日期 + 1 天
- F = 消费天数，**同日多单合并计 1 次**（防刷单/拆单扭曲）
- M = 净消费额（实付 − 退货）

**分群阈值的权衡**：五分位打分 1~5 后，初版用 ≥3 记「高」，结果「重要价值客户」占 40%（单维 60% 概率且 F/M 正相关），业务上不可解释。改为 ≥4（前 40%）后分布符合零售常识：头部客群 15%~20% 贡献 40%+ GMV。这是「口径影响结论」的典型案例。

**两套时间窗并存**：RFM/画像用全量 2 年（描述现状），流失模型用 270 天观察窗 + 90 天标签窗（预测未来）。二者基准日不同是**正常设计**，但必须写进指标文档，否则会被质疑「RFM 说他是重要客户，模型却预测他流失」。

### 2.4 流失预测：方法论最重的模块

**防泄漏设计**（`models/churn.py::build_cohort_samples`）：
- 特征只取观察窗（截止日前 270 天），标签只看标签窗（截止日后 90 天），物理隔离；
- 滚动 3 期 cohort（2021-10 / 2022-01 / 2022-04）扩充样本并验证时间稳定性；
- **按时间切分**训练/测试（前 2 期训练、末期测试），禁止随机切分——随机切分会让同一会员的行为模式同时出现在训练与测试中，AUC 虚高。

**类别不平衡**：基线流失率 35.7%，用 `scale_pos_weight` + 阈值调优，不做盲目过采样（SMOTE 在表格业务数据上容易造出不可能样本）。

**业务导向评估**：运营团队只发得动 Top 20% 名单，所以主指标是 **Top20% 捕获率（46.77%）与 Lift（2.34）** 而非只看 AUC。一个关键认知：**Lift 的理论上限 = 1/基线率**，基线 36.8% 时上限仅 2.72，因此「lift≥3」的验收标准在数学上不可达——验收口径修正为「AUC 超基线 +0.03 且达到上限 85% 以上」。这个修正过程本身就是面试加分点。

**可解释性**：装了 `shap` 就用 `TreeExplainer`（全局重要性抽样 5000 条 + **末期 cohort 全量逐会员归因**，实测覆盖 22,777/22,777 = 100%）；没装则降级 `permutation_importance` 并**显式告警**，不静默失败。随机森林的精确 Tree SHAP 很慢（35 秒），改用 Saabas 近似后 0.1 秒，与精确值相关系数 **0.9992**。

### 2.5 关联规则：内存控制是工程分水岭

SKU 级 5000 维 one-hot × 25 万篮子必然爆内存。分层方案：
- **品类级全量**（60 维）：FP-Growth 直接跑，作为主输出（业务可读性最高）；
- **SKU 级**：仅取销量 Top 300 SKU + 篮子长度 ≤30 截断 + 分门店分批（P1 方案，计划 §8.3）；
- 算法选 **FP-Growth 而非 Apriori**：前者两次扫描 + FP-Tree 压缩，比 Apriori 的候选集爆炸快一个量级。

参数：min_support 1%、min_confidence 30%、lift>1.5。注意三个参数的业务含义：support 是「值不值得管」（覆盖太小的规则没有运营价值），confidence 是「推得准不准」，lift 是「是不是真关联」（>1 才是正相关，仅看 confidence 会被热销品欺骗）。

### 2.7 趋势分析：同比 / 环比 / 季节性

**口径**：环比 = 本期/上一期−1；同比 = 本期/上年同期−1（按月份/季度序号分组 pct_change，见 `reports/core_reports.py::add_growth_columns`，有单测 `test_reports.py`）。

**数据窗口设计**：2020-01 ~ 2022-07 共 31 个月（非完整年度）——1~7 月三年可比、8~12 月两年可比；**2022Q3 仅含 7 月，属不完整季度，同比数值是口径假象，报告中显式剔除**。这是真实项目里最常见的趋势分析陷阱。

**季节性**：生成器内置月度权重（春节 1~2 月、618、双 11/年货节为高峰，3~4 月低谷），实测双 11 月 GMV 为淡季 2.9 倍。季节性强的业务里，环比结论必须让位于同比。

**产出**：`mart_monthly` / `mart_quarterly` 两张集市表（含 mom/yoy 列），图 01b（月度同比分组柱状图）、图 01c（季度 GMV + 同比标注），Excel sheet 1/1b，看板首页趋势区。

### 2.6 工程规范

- **可复现**：种子统一 `SEED=42`；`make all` 一键全链路约 40 秒；清空数据重跑指标完全一致
- **测试**：19 个 pytest 用例，其中 `test_leakage.py` 专门断言「recency 不来自标签窗」（若泄漏，member 1 的 recency 会是 -14 天）

## 三、开发与合作过程还原

本项目按「乙方数据服务公司交付分析项目」的流程开发，全过程可还原为 6 个阶段：

### 3.1 需求澄清与计划评审

先产出《项目编写计划》，再做**需求对照评审**（计划 §0）：把甲方的 10 条原始需求逐条映射到计划章节，评审出 14 项问题（6 项严重），包括数据规模自相矛盾、流失标签窗口未定义、关联规则内存爆点等。**教训：先评审再动手，避免返工**——例如「Lift≥3 数学不可达」若在交付后才发现，会演变成交付事故。

### 3.2 里程碑制交付（对应计划 §11）

| 阶段 | 交付物 | 验收方式 |
|---|---|---|
| 数据基座 | 生成器 + ETL + 质量报告 | 脏数据埋点 100% 被捕获 |
| 报表与 EDA | 5 类核心报表 + Excel | 口径入指标文档 |
| RFM 与画像 | 8 客群 + 20 标签宽表 | 客群分布符合零售常识（头部 20% 贡献 40%+） |

| 报告 | 决策建议 8 条 | 每条附数据证据 + 测算假设声明 |

### 3.3 真实踩坑与返工记录（面试可讲的「过程感」素材）

1. **客群分布失衡返工**：首版 RFM 用 ≥3 为「高」，重要价值客户占 40%，业务评审不通过 → 改 ≥4 阈值并重跑，记录口径变更原因；
2. **环境依赖返工**：lightgbm 报 `libomp.dylib not found`，本机无 brew → 复用 sklearn 自带的 libomp 解决，并写入 README 供复现者参考；
3. **pandas 版本兼容**：pandas 4 弃用 `dt.dayofweek`，CI 式告警驱动改为 `day_of_week`（3 处）；
4. **验收标准修正**：评审发现「Lift≥3」在基线流失率 36.8% 下不可达（上限 2.72），与甲方（业务方）对齐后改为「AUC 超基线 +0.03 + 达上限 85% 以上」；
5. **数据边界越界修复**：「一次性」人群的活跃终点 `reg_day + 30 天` 可能超出数据窗口（出现 2022-08 的越界交易），补 `clip` 后重跑；
6. **代码整洁**：生成器初版留有占位死代码，评审后清理（计划要求「先设计后编码」，评审兜底）。

### 3.3.1 v3.3 全量核查：「测试全绿」不等于「结果正确」★ 最值得讲的返工记录

> 这是本项目**含金量最高**的一段工程经历，因为它展示的是「**如何怀疑自己已经完成的东西**」。

**背景**：v3.1/v3.2 声称交付了 18 项能力，pytest 138 例全绿、覆盖率 70.72%。
我决定做一次**全量代码—文档—产物三方一致性核查**：逐条把 18 项交付与真实代码、真实产物对上。

**核查方式**：不是读代码，而是**拿两套独立口径算同一个数，再逐行比对**。

**结果：查出 5 个「不报错」的缺陷**：

| 缺陷 | 为什么测试没抓到 |
|---|---|
| `potential_index` / `lifecycle_stage` **整体错位一格**（99.997% 的会员拿到的是下一个会员的潜力指数） | 索引值都是合法 member_id，断言和单测全部通过 —— 只有拿「按 member_id 建索引重算」的第二实现逐行比对才暴露 |
| 决策建议报告**混用对照模型与主模型的指标**（AUC 取 GBDT 的 0.8179，增益取 RF 的 +0.0305） | JSON 里两个字段都是合法数字，模板渲染也成功 —— 只有把报告文字与 `metrics_churn.json` 交叉核对才发现「已达标」与「无一达到 +0.03」并排出现 |
| S1 建议**借用了 S2 的测算占位符** | 模板能渲染、占位符齐全 —— 只有拿公式反算金额才发现对不上 |
| 门店报表三列**整体错位一格**（门店 1 为空，门店 k 拿到门店 k-1 的值） | NaN 只出现在第一行，容易被当成「该门店无会员」 —— 只有独立复算门店 1 的增长率才发现 |
| **`.gitignore` 误伤源码包** ★（最严重） | `git clone` 出来的仓库**整个 `retailinsight/reports/` 包不存在** —— `--stage all` 直接 ModuleNotFoundError | 本地一切正常、pytest 全绿、文档齐备 —— **只有 `git clone` 到干净目录实测才会暴露**。`.gitignore` 的 `reports/` 没锚定仓库根，把源码包一起忽略了 |

**还查出 3 处「交付了但没产出」**：
质量报告 HTML 的代码写完了、文件却不在仓库里（旧测试还会 `unlink` 掉真实产物）；
关联规则网络图**没有任何生产代码调用**，只有测试调它；
客群画像卡片与差异论证**不在 CLI stage 清单里**，只能手工跑模块。

**以及 11 处文档与实测脱节**（含一处自相矛盾：指南里同时写着「主模型已改成随机森林」和「随机森林 AUC 略优但我没换主模型」）。

**我做的三件事**：
1. **修代码 + 补回归测试**：5 个缺陷全部修掉，每个都配了「用第二实现逐行比对」的回归用例（`tests/test_v33_audit_fixes.py`）；
2. **把结论改成由代码生成**：报告里的模型结论段、聚类特征空间对比表，都不再写死字符串 —— 数据一更新，结论自动跟随；
3. **把文档全部回填**：11 处脱节逐条改正，并在计划文档里立 §0.9~§0.11 三节留档。

**这轮最大的收获是一句话**：
> **「测试全绿」只能证明「代码按预期执行了」，不能证明「结果是对的」。**
> 我这 5 个缺陷全部不报错、全部测试全绿 —— 它们是**用两套独立实现算同一个数、再逐行比对**才抓出来的。
> 这也正是我引入 DuckDB 的真正理由：**不是为了用新技术，而是为了多一个独立实现来自证 pandas 的结果正确。**

**面试怎么讲这题**：
「我做完 v3.2 的时候 138 个测试全绿，觉得可以交付了。后来我专门花一天做了一次全量核查，把 18 项交付逐条跟真实产物对了一遍 —— 查出 5 个不报错的 bug，其中一个让 99.997% 的会员拿到了别人的潜力指数，最狠的一个是 `.gitignore` 把源码包忽略了 —— clone 出来整个交付物跑不起来。而所有测试都是绿的。
我从这件事里得到的结论是：**测试只能证明代码按你写的执行了，不能证明结果是对的。要证明结果对，必须有第二套独立实现去交叉验证。** 那个 bug 的根因是索引对齐 —— RangeIndex 和 member_id 混用，这个坑我在这个项目里踩了三次，所以我现在把它当成一条纪律：任何 join 前先问『这两边的索引是一回事吗』。」

> 详见 `项目编写计划.md` §0.9（5 个缺陷）、§0.10（3 处「交付了但没产出」）、§0.11（11 处文档脱节）。

### 3.3.2 v3.4 第二轮复核：v3.3 的复现验证**做得还不够**（4 个缺陷）

> 这一段是 v3.3 的续集，价值在于展示「**我如何发现自己的验证方法本身有漏洞**」。

**v3.3 的做法**：`git clone` 到干净目录再跑一遍，自认为解决了「仓库不可复现」。
**v3.4 发现的问题**：那次 clone 之后，我用的仍是**已装好全部依赖的 venv** —— 干净目录只是干净，环境并不干净。

于是换一个提问方式：**「别人新装一台机器，照 README 走一遍，会不会崩？」**
答案是会，而且是四处（第四个是复核过程中顺手逮到的）：

| # | 缺陷 | 症状 | 为什么「本机全绿」 |
|---|---|---|---|
| 13 ★ | **依赖漏声明** | `plotly` / `shap` 代码里 import 了，`pyproject.toml` 一个字没写；`duckdb` 被放进可选组 `p1`，而 `warehouse` 在 `--stage all` 的**必经路径**上 → 新机器 `make all` 崩在 warehouse，看板一启动就 ImportError，`uv.lock` 还停在旧的 62 包 | 我的 venv 里这些包都装过（历史上 `pip install` 过），**import 得通 ≠ 依赖声明过** |

  并加了一条 **AST 级测试**：扫描 `retailinsight/` 全部 import，断言每个第三方包都在主依赖里。

  修完第一眼看到 `transactions.member_id` 是 **2.9682% → 2.9831%**（清洗后反而略升），

- 产物：HTML 路径改为跟随 md 入参，并加了一条「写 tmp 前后真实产物字节必须不变」的断言 ——
  **一个缺陷修完要问「同一根因还有别的形态吗」**，这条就是 v3.3 漏掉的那半个形态。

**面试怎么讲这题（比技术细节更重要的是这一层）**：
「我第一轮核查做的是 `git clone` 到干净目录，当时觉得已经把可复现性证完了。第二轮我换了个问法：**别人新装一台机器，照 README 走一遍会不会崩？** 结果发现 clone 干净了但环境没干净 —— 我的 venv 里那些包都是历史上随手装过的，`pyproject.toml` 根本没写。这让我意识到一件事：**验证要验证『别人的路径』，而不是『我的路径再走一遍』**。所以我不只是补了依赖，而是写了一条 AST 测试去扫全部 import —— 把『我记得声明过』变成『机器每次都替我检查』。」

## 四、面试题与详细回答（35 题）

### A. 项目背景与业务理解（5 题）

**Q1. 用一分钟介绍这个项目。**

RetailInsight 是模拟乙方数据服务公司为连锁商超做的会员画像分析项目。甲方痛点是会员体系形同虚设、营销粗放、采购凭经验。我用合成数据生成器构建了 31 个月（2020-01 ~ 2022-07）3.6 万注册会员、31.4 万笔交易、217 万明细的数据集（含 8 类人群、关联组合与季节性埋点），完成了清洗、DuckDB 星型数仓、月度/季度环比同比趋势分析、RFM 8 类客群分群、38 个画像标签（含 CLV）、流失预测（**主模型由验收线自动选出随机森林，AUC 0.830，Top20% 捕获 46.77% 流失者**）和 FP-Growth 关联规则（品类级 177 + SKU 级 48 + 分门店 1,092 条），最终交付 8 条含量化测算的运营与采购建议、Excel 报表、客群画像卡片和 Streamlit 看板。核心价值：头部 18.3% 会员贡献 42.5% GMV，37.8% 会员处于流失风险，建议据此做分层运营和精准促销。

**Q2. 为什么用合成数据而不是开源数据集？**

两条腿走路，合成数据为主：① 开源零售数据集（Dunnhumby 是美国、Online Retail II 是英国电商）字段和业态与中国商超故事不匹配；② 合成数据可以**埋点验证**——预设 8 类人群和 4 组关联组合，模型结果能与先验对照，证明「聚类/关联挖掘确实找回了真实结构」，这是开源数据做不到的；③ 开源数据集并未弃用，`io/schema.py` 预留了 Dunnhumby/UCI 的 canonical schema 映射层，ETL 一套代码可插拔复用。另外合成数据规避了 Dunnhumby 的「仅非商业研究」许可限制。

**Q3. 这个项目最大的业务价值是什么？**

两个可量化的点：① 发现 37.8% 会员处于流失风险，流失模型圈出 5,014 名高危会员，按 S1 测算挽回 GMV 24.1~48.1 万元；② 促销从全员发券改为按 `discount_sensitivity` Top 20% 精准投放，券成本预计下降 **80%**（28.9 万元）。方法论上的价值是把「分析」闭环到「决策」：每条建议都是发现→证据→建议→测算四段式，测算参数标注为假设值并声明需 A/B 验证。

**Q4. 如果甲方说"你们的模型我们不放心"，你怎么推进？**

三步：① 用可解释性建立信任——用 `shap.TreeExplainer` 给出全局重要性（验证集抽样 5000 条）与**逐会员 Top 归因**（`mart_churn_score.top_shap_feature` 列），可对任一高危会员解释「为什么判他流失」；② 小步验证——先对 Top 20% 名单（约 1000 人）做一个月挽留试点，设对照组，用真实挽回率替换测算中的假设值；③ 口径对齐——把指标文档给甲方数据团队评审，尤其是「流失」的定义（90 天无交易是否符合他们的业务认知）。

**Q5. 非会员交易占比只有 3%，这说明了什么？**

两层解读：业务上说明该商超交易几乎全走会员通道（会员渗透率高），会员运营是唯一抓手，但也意味着「拉新获客」数据盲区大——建议甲方补充非会员识别手段（如支付账号绑定）。分析上这也是我在 ETL 中不删除缺失会员ID 交易的原因：3% 虽少，但它衡量的是「非会员客单价 vs 会员客单价」的差异，删了就丢了这个指标。

### B. 数据工程（6 题）

**Q6. 数据生成器怎么设计的？为什么要"埋点"？**

生成器全向量化（numpy poisson 频次 + repeat 展开 + 逆 CDF 采样时段分布），scale=1 时 12 万会员/130 万交易秒级完成。埋点分三类：① 人群埋点（8 类 personas，参数化频次/客单/时段/生命周期），用于对照验证聚类是否找回真实结构；② 关联埋点（4 组商品组合按 5%~8% 概率注入篮子前两件），验证关联规则链路——4 组全部回收；③ 脏数据埋点（重复 0.5%、会员ID 缺失 3%、退货 1%、品类别名 2%、逻辑冲突 0.5%），为清洗环节提供素材，也让数据质量报告有真实内容可写。

**Q7. 清洗环节有哪些规则？取舍逻辑是什么？**

5 类规则，每类都有单测：① 重复：按 txn_id 去重留首条；② 缺失：会员ID 缺失不删、归入「非会员」客群单独分析（删了会低估 GMV）；③ 异常：负金额打 is_return 标记单列分析（退货率本身是画像标签）；④ 口径：品类别名映射表归一（覆盖率 100%）；⑤ 逻辑冲突：交易早于注册时间打异常标记、分析时剔除。极端值按 P99.9 截断并记录剔除率（验收 ≤3%）。核心原则：**能标记的就不删除，删除必须有业务理由且可追溯**。

**Q8. 为什么选 parquet + DuckDB 而不是 CSV + SQLite？**

parquet：列存 + 压缩（体积约为 CSV 的 1/5~1/10）、带 schema 和类型、支持谓词下推只读需要的列/分区。DuckDB：分析型列存引擎，直接 SQL 查询 parquet 文件（不用先导库），窗口函数齐全（算 RFM 排名很方便），单节点聚合性能远超 SQLite（行存 OLTP 引擎，不适合分析）。SQLite 只作为对外分发的轻量备选。这个对比本质是 OLTP vs OLAP 的选型问题。

**这里要如实说明现状**：parquet 是**实际使用**的（`retailinsight/io/loader.py` 统一读写，明细已按 `txn_month` 分区），DuckDB **也已真正接入**（`retailinsight/etl/warehouse.py`）：建了 `dim_member/dim_product/dim_store/dim_date` + `fact_transactions` + `fact_transaction_items` 星型模型，用 DuckDB 的窗口函数**重算了一遍 RFM**，并与 pandas 版做**逐行一致性断言** —— 实测 35,650 行、5 个字段零差异，外键零孤儿。

DuckDB 在这里的价值不是炫技，而是**用第二实现来自证 pandas 结果正确**：两套独立代码算出同一个数，才说明口径没漂移。

**Q9. 数据量涨 10 倍（千万级明细）怎么办？**

预案分四步，**已落地 / 未落地**要分清：① dtype 优化（整数降位 / float32 / category）✅；② 明细按交易月份分区、窗口期只加载所需分区 ✅（实测读 3 个月仅占全量 **20.2%**）；③ 聚合下沉到 DuckDB SQL ✅（星型模型已落地，RFM 用 SQL 重算并做一致性断言）；④ `--scale 5` 压测报告 ✅（`docs/性能报告.md`：12 个 stage 全部跑通，合计 12,450s，峰值内存 **7.29 GB**）。

**压测报告本身就是答案**：在 8GB 内存的普通开发机上，scale 5（60 万会员 / 528 万交易 / 3,644 万明细）**能跑完**，但峰值已到 7.29GB —— 再往上（亿级）才是分布式（Spark）的领地，单机 DuckDB 在亿级 groupby 上仍有一战之力。

**Q10. 怎么保证数据质量可持续（不是一次性清洗）？**

三道防线：① 质量报告自动化——每次 ETL 重跑都重新生成前后对比报告（行数、缺失率、剔除率），剔除率超 3% 需要人工解释；② 清洗规则单测化——上游数据形态变化（比如出现新品类别名）会让测试变红，而不是静默产出脏结果；③ 别名映射表覆盖率要求 100%，出现未映射品类直接报错而非放行。

**Q11. 你们的表结构怎么设计的？**

星型模型：事实表 `transactions` + `transaction_items`，维表 `members`（会员属性）、`stores`、`products`（品类三级）、`dim_date`。集市层 4 张宽表：`mart_rfm`、`mart_member_profile`、`mart_churn_score`、`mart_basket_rules`。设计原则：明细层保持原子粒度（一行一商品），所有聚合在集市层完成，维表缓慢变化属性（如会员年龄段）用快照而非覆盖。

### C. RFM 与用户画像（5 题）

**Q12. RFM 三个指标的口径是什么？有哪些容易踩的坑？**

R = 基准日 − 最近消费日（基准日 = 数据最大日期+1，不是"今天"，否则用历史数据复算时口径漂移）；F = 消费天数，**同日多单合并计 1 次**（商超高频场景下不合并会把拆单用户误判为高频）；M = 净消费额（实付−退货，不算退货会高估退货率高的人群价值）。坑：① 基准日不固定导致报表不可复现；② F 用订单数而非消费天数；③ M 不扣退货。三条坑本项目都规避了，口径写入指标体系文档。

**Q13. 五分位打分后怎么映射 8 类客群？阈值怎么定的？**

R/F/M 各自五分位打 1~5 分，≥4（前 40%）记「高」，按 2×2×2 映射 8 类（重要价值/发展/保持/挽留、一般价值/潜力/一般保持/流失风险）。阈值是调过的：初版 ≥3 导致单维 60% 为高、且 F/M 正相关，「重要价值客户」占 40%，业务上不可接受（头部客群通常 15~20%）；改 ≥4 后头部 18.5% 贡献 42.7% GMV，符合零售帕累托常识。**教训：分群阈值不是数学问题，是业务可解释性问题**。

**Q14. RFM 规则法和聚类法怎么选？**

互补而非替代：规则法（五分位映射）业务可解释性强、口径稳定、可对外沟通，作为 P0 基线；聚类（K-Means）能发现规则法覆盖不到的结构（比如「高频低额」客群在规则法里被 M 维度淹没），作为 P1 补充。落地用列联表 + 调整兰德指数做一致性对照：高度重合的部分增强信心，分歧的客群单独做画像解读。最终对外交付仍以规则法 8 类为主——运营团队需要一个背得下来的分类体系。

**Q15. 画像标签怎么设计才有业务价值？**

四条原则：① 分层——基础属性/消费能力/行为偏好/生命周期四层，从「他是谁」到「他值多少」到「怎么触达」；② 每个标签必须能回答一个运营动作（如「折扣敏感度」直接决定发券面额，发不了动作的标签不做）；③ 口径可复算——全部在 `features/` 层计算，文档记录出处；④ 分级交付——P0 20 个先上线，P1 20 个（CLV、价格弹性等）迭代补充，避免一次性铺 40 个导致工期失控。

**Q16. 画像是离线 T+1 还是实时？怎么选？**

本项目是离线批处理（月度/周度跑批），理由：商超会员运营动作（发券、回访、采购调整）的决策周期是天到周级，实时画像的边际价值低而成本高（流处理、特征在线存储）。演进路径：先把离线宽表跑稳、指标口径被业务认可，再把「触发式」场景（如大额退货后实时降级权益）做成近实时，其余保持 T+1。

### D. 机器学习（8 题）

**Q17. 流失标签怎么定义？为什么这么定义？**

观察窗（270 天）内活跃（≥1 笔交易）、标签窗（90 天）内 0 交易 → 流失=1。理由：商超高频消费业态下，90 天不进店对活跃会员是强流失信号；90 天而非 30 天是因为「周末囤货」「季节性」人群天然有长间隔，窗口太短会把正常波动误判为流失。窗口长度本身是业务参数，正式交付时会与甲方对齐（也可用生存分析确定各客群的自然回购周期分位数来定）。

**Q18. 怎么防止数据泄漏？**

三层：① 时间物理隔离——特征只取观察窗、标签只看标签窗，`test_leakage.py` 有专项断言（若泄漏，某会员 recency 会算出负数 -14 天，测试直接红）；② **三向**时间切分（5 期 cohort：前 3 期训练、第 4 期验证、末期测试），禁止随机切分（随机切会让同一会员行为模式同时出现在两侧，AUC 虚高）；验证集用于超参搜索与阈值调优，测试集全程不参与选择；③ 滚动多期 cohort 本身也是稳健性验证。**代价与结论要说清楚**：在固定可用 cohort 下，加一个验证集等于少一期训练数据，AUC 相对增益会掉 0.007~0.008；我把窗口拉长到 5 期、多留 1 期训练来缓解（`TRAIN_COHORTS=3`）。为此专门跑了 6 组切分×特征的敏感性实验（`scripts/exp_churn_sensitivity.py`）：**+0.03 这条验收线在当前数据窗口与特征族下不可达**（最佳配置 +0.0272），因为特征从 12 扩到 31 维后 LR 基线同步变强、相对增益被摊薄。**这是天花板问题，不是调参问题** —— 要突破得延长可标注窗口或引入新特征族。

**Q19. 主模型为什么是随机森林，不是 LightGBM？**

这题我的答案是：**不是我选的，是验收线选的。**

① **为什么不用深度学习**：表格数据 + 31 维手工特征，GBDT/树模型在这个量级仍是 SOTA，深度学习没有优势且训练和部署成本高；业务方要的是「为什么他流失」，树模型能直接给出特征重要性和 SHAP。

② **LightGBM 为什么降为对照**：最初主模型是 LightGBM（AUC 0.818），但它相对 LR 基线的增益只有 **+0.019**，**打不到计划里写的 +0.03 验收线**。我为此跑了 6 组「切分方式 × 特征数量」的敏感性实验，增益区间 +0.0124~+0.0194 —— 说明在 GBDT 这一族里 +0.03 是当前数据窗口下的天花板，不是调参问题。

③ **随机森林反而达标**：RF AUC **0.830**、KS 0.493，相对 LR 基线 **+0.0305**，刚好过线。于是我把选型规则**写死在代码里**（`models/churn.py::select_main_model`）：先筛出「AUC ≥ 基线 + 0.03」的达标组 → 取其中 KS 最高者 → 全不达标才取 AUC 最高者并标记未达标。每次跑出来的结论都一样，可复现、可向甲方解释。

④ **代价也如实说**：RF 的精确 Tree SHAP 很慢（5000 行 × 300 树实测 35 秒），改用 Saabas 近似后 0.1 秒，与精确值相关系数 **0.9992** —— 对「Top 归因特征」这个用途完全够用。LR 作为可解释基线保留（AUC 0.798，标准 KS 0.450）。

> 这一段我更想讲的不是「我选了哪个模型」，而是**「选型规则被写进了代码」**这件事本身。模型选型最容易被「我觉得 X 更好」左右；规则化之后，**验收标准直接决定交付什么**，而且谁都能复算出同一个结论。

① 数据形态：表格数据 + 31 维手工特征，树模型在这个量级仍是 SOTA，深度学习没有优势且训练/部署成本高；② 可解释性：业务方要「为什么他流失」，树模型能直接给出 SHAP；③ 效率：分钟级训练，便于每月跑批。LR 作为可解释基线保留（AUC 0.7995，标准 KS 0.4521）。

**对照结果要如实讲**：LightGBM AUC 0.8179 / KS 0.4836，RandomForest AUC 0.8300 / KS 0.4936 —— **随机森林在 AUC 上优 0.0121，且增益刚好越过 +0.03 验收线**。所以主模型换成了随机森林 —— 这不是「我更喜欢哪个」，而是验收线逼出来的选择。

> ⚠️ **本节的旧版本曾写着「随机森林 AUC 略优 0.005，但我没有因此换主模型，理由是 GBDT 成本更低」** ——
> 这与上一段「主模型已按验收线改成随机森林」**自相矛盾**。
> v3.3 核查时发现（见 `项目编写计划.md` §0.11 第 5 条），已按实际实现改写。
> **教训**：模型选型这类「结论性表述」不能手写，一旦换模型，文档里所有「为什么选它」的论证都会变成自证 —— 必须由代码生成结论，文档只引用产物。

**Q20. 类别不平衡怎么处理的？为什么不用 SMOTE？**

基线流失率 36.8%，不算极端不平衡：GBDT 用 `scale_pos_weight`（实测正负样本比 2.11），LR 用 `class_weight="balanced"`；阈值不拍脑袋 —— 在**验证集**上按业务成本最优求解（漏判:误触 = 8:1，与决策建议 S2 同口径），得到行动名单阈值 **0.28**、中危 **0.47**、高危 **0.63**。不用 SMOTE：① 表格业务数据上插值会造出「不可能的样本」（比如消费频次 2.7 次）；② 我们的评估是排序导向（捕获率/Lift）而非 0/1 分类导向，重采样的收益主要在硬分类指标上；③ 36.8% 的正例比例本身足够学习。

**Q21. 评估指标为什么强调 Lift 和捕获率而不是只看 AUC？**

AUC 衡量整体排序能力，但业务动作有预算约束——运营团队每月只触达得动 Top 20% 名单，所以关键是「名单头部准不准」：Top20% 捕获率 47.1%（花 20% 的成本覆盖近一半流失者）、Lift 2.35（命中率是随机的 2.35 倍）。还修正过一个认知错误：最初验收写 Lift≥3，但 Lift 上限 = 1/基线率 = 2.72，该标准数学上不可达，改为「AUC 超基线 +0.03 且达上限 85% 以上」。**评估指标必须和业务动作的成本结构对齐**。

**Q22. 模型上线后怎么监控和迭代？**

① 每月跑批后用最新一期 cohort 做时间外推验证，监控 AUC/捕获率衰减（概念漂移：促销季、新开店都会改变行为分布）；② 特征分布监控（PSI），输入漂移先于效果衰减暴露；③ 挽留动作的回收数据（发了券是否回来消费）回流为新的标签来源，形成闭环；④ 衰退超阈值时滚动重训，特征体系保持稳定以保证口径可比。

**Q23. 关联规则为什么用 FP-Growth 不用 Apriori？参数怎么定的？**

Apriori 逐层生成候选集，60 品类下 2 项集 1770 个、3 项集 3.4 万个，候选集爆炸；FP-Growth 用 FP-Tree 压缩 + 两次扫描，快一个量级。参数：min_support 1%（覆盖太小的规则没有运营价值——「值不值得管」）、min_confidence 30%（「推得准不准」）、lift>1.5（「是不是真关联」，只看 confidence 会被热销品欺骗——任何东西都和粮油米面"相关"）。最终 177 条规则（v3.5 的品类乘子让门店/人群品类结构分化，共购对随之变少：373 → 177），4 组预埋组合全部回收，验证了链路有效性。

**Q24. 聚类怎么评估？没有标签怎么知道分得对不对？**

三重视角，全部落到代码里（`retailinsight/models/cluster.py`）：① 内部指标——轮廓系数（验收 ≥0.35）与最小群占比 ≥2% 作为**硬护栏**，不满足就退到次优 K；② 外部对照——与合成数据预埋的 8 类先验人群做列联表 + ARI/NMI，量化「找回了多少真实结构」；③ 业务可解释性——每个群必须能命名成一句人话（高价值活跃 / 低频低额 / 沉睡流失 / 一般维持），重名自动加序号。

**最值得讲的上界检验**：我先用生成器埋的**真实 8 类人群**当标签算了一次轮廓系数（神谕上界），结果是 **-0.056**。这说明「消费体量」这类特征在数学上就无法分离行为型人群 —— 再调 K、再调参都到不了 0.35。因此我在 3 个候选特征空间（base6 / rfm3 / rfm3+行为）里择优，最终落在 **rfm3、K=4、轮廓系数 0.416（达标）、ARI 0.135**，并把「为什么上限只有 0.14」写进结论：8 类人群中的「促销敏感 / 周末囤货 / 季节性」在 RFM 上本就重合，要再往下拆必须上行为时序特征（计划 §7.3 的 P1 扩展标签）。

### E. 统计与评估（4 题）

**Q25. Top 品类 5 个就占 53% GMV，帕累托分析的结论边界在哪？**

结论：A 类 10 个品类（贡献 70%）保货架，C 类尾部优化。边界：① 销售贡献不是唯一维度，必须叠加毛利和引流角色——纸尿裤可能毛利低但引流强，不能简单淘汰；② 品类间有关联结构（啤酒-纸尿裤），淘汰前先看关联规则里的角色；③ ABC 是静态截面，季节性品类（火锅底料）会在冬季误判为 C 类，需要滚动窗口复核。所以报告里 S6 的淘汰标准是「90 天零动销 + 毛利贡献」双维度，而非纯销售排名。

**Q26. 报告里的"挽回 GMV 17~34 万"怎么算的？可信吗？**

公式：高危会员数 3,574 × 触达率 80% × 挽回率 10%~20% × 月均消费恢复值 100 元 × 6 个月。其中触达率和挽回率是**假设值**（行业经验区间），不是模型算出来的；月均消费恢复值来自「一般保持客户」的实测水平。可信度的正确处理方式：给区间而非点估计、显式标注假设、并设计小步试点（Top 700 人 + 对照组）用真实回收数据替换假设参数。**拍脑袋给点估计算术上再精确也是错的**。

**Q27. 同比增长能直接外推吗？**

不能。本项目 2021Q4 同比 +84.4%、2022Q2 同比 +69.7% 的高速增长，主要驱动是会员规模扩张（注册均匀分布导致前期会员基数小），属于结构性放量而非可持续增速。趋势外推只能作为情景假设（「按当前增速会怎样」），必须叠加约束：会员增长会触顶、流失风险客群已达 38.0%。另外同比有两个口径陷阱本项目专门处理了：① 数据为 31 个月非完整年度，2022Q3 仅含 7 月，其「同比 -41.8%」是口径假象，报告中显式剔除；② 强季节性（双 11 月为淡季 2.9 倍）下环比意义有限，跨年判断必须看同比。

**Q28. 显著性怎么考虑？比如客群间客单价差异是不是真的？**

本项目是描述性分析为主，显著性检验用在这些地方：① 客群间客单价/频次差异用 Kruskal-Wallis（非正态、方差不齐）+ 事后两两比较；② 关联规则的 lift 辅以置信区间（bootstrap 篮子重采样），避免小支持度规则的 lift 虚高；③ 未来 A/B 试点（挽留券组 vs 对照组）用两比例 z 检验评估挽回率差异。核心原则：**样本量大时差异几乎总是"显著"，所以必须同时报告效应量**（差多少、占比多少），不能只看 p 值。

### F. 工程与协作（6 题）

**Q29. 项目怎么保证可复现？**

四层：① 种子统一 `SEED=42`，生成器/模型/切分全部注入，清空数据重跑指标完全一致（实测验证过）；② 依赖锁定在 pyproject.toml，Python 3.11+；③ 单一入口 `make all`（14 个 stage，约 2.5 分钟）+ `make dashboard`（交互式看板）；④ 环境坑写进 README（如 lightgbm 需要 libomp，本机用 sklearn 自带的库解决）。

**Q30. 测试覆盖了什么？为什么特别强调防泄漏测试？**

19 个用例五类：清洗规则（去重/别名/退货/缺失/逻辑冲突/截断）、RFM 口径（toy 数据验证 F 同日合并、M 净额、分群映射）、防泄漏（标签正确性 + recency 不为负 + 特征列完整）、趋势口径（环比/同比/季度同比的 toy 验证）、schema 一致性（60 品类、别名指向规范名、人群权重和为 1）。防泄漏单列是因为它是建模里最容易犯且危害最大的错误——泄漏的模型离线指标漂亮、上线即崩，而且 review 代码很难看出来，只有测试能兜底（用「如果泄漏 recency 会是负数」这种确定性断言）。

**Q31. 多人协作时最容易出什么问题？怎么防？**

最常见的是**口径漂移**：同一个「复购率」，分析师 A 用 30 天窗口、B 用 90 天，报表打架。防法：① 指标先入《指标体系.md》再写代码，文档有业务定义+窗口+代码出处；② 计算逻辑收敛在 `features/` 包，看板/报表/notebook 只调用不重算；③ 交付物分层——分析师用 notebook，业务方只给 Excel 和报告，减少口径接触面。其次是数据变更无通知：上游 schema 变了下游静默出错，用 schema 单测（test_schema.py）挡。

**Q32. 看板为什么不直连明细表？**

三个原因：① 性能——看板只读 `data/marts/` 的聚合宽表，加 `@st.cache_data` 缓存，首屏 <3 秒；直连 219 万明细每次操作都重算，不可用；② 口径——明细直连意味着看板里要重写指标逻辑，违背单一真相源原则；③ 职责分离——看板是展示层，数据正确性由离线链路 + 测试保证，展示层不做业务计算。

**Q33. 这个项目如果继续演进，优先级是什么？**

v3.0 收敛的 **9 项在 v3.1 已全部交付**（`项目编写计划.md` §二.3）：① DuckDB 星型模型（用第二实现自证 pandas 的 RFM 正确，实测 35,650 行零差异）；② 下载器 + schema 映射生效（一份 ETL 通吃三源）；③ 明细按交易月份分区（读 3 个月仅占全量 20.2%）；④ plotly 交互图 + 点选下钻；⑤ 客群画像卡片（8 群各一页）；⑥ CLV 简化模型，把「价值」从历史贡献升级为未来预期，校准挽留预算；⑦ GMM / DBSCAN 与 K-Means 对比（0.4165 / 0.2536 / 0.0422 → 选 K-Means）；⑧ `--scale 5` 性能压测报告（12 stage 全通，峰值 7.29GB）；⑨ SKU 级 + 分门店关联规则（SKU 48 条 + 分店 1,092 条，v3.6 重算；v3.1 时为 1,398 条）。**公网部署已取消** —— 作品集以本地可复现 + 已执行的 5 个 Notebook + Excel + PNG 图作为物证链即可。

**若要再往下做**，我的优先级是：① 把 SKUs 的**同品类共购**也做成埋点（当前 SKU 级信号全靠 4 组跨品类锚点）；② 引入行为时序特征（跨店消费、复购周期、间隔方差）—— 这才是聚类 ARI 上不去 0.14 的真正解法；③ 换成真实业务数据后重跑全部阈值（当前 min_support / min_confidence 是在合成数据上调的）。

**Q34. 你在项目中遇到的最大困难是什么？（开放题，建议答法）**

建议答「Lift 验收标准不可达」这个：初期按行业口径写「Lift≥3」，跑完模型发现最高只有 2.35，排查后确认是数学上限问题（Lift 上限 = 1/基线流失率 = 2.72），不是模型不行。处理过程：推导上限公式 → 用数据验证（基线 36.8% → 上限 2.72）→ 与业务方对齐改为「AUC 超基线 +0.03 且达上限 85% 以上」→ 修正文档和验收标准。体现的素质：**不盲从行业惯例、能用第一性原理排查、会管理预期**。备选答案：libomp 环境问题（体现环境排障能力）或客群分布失衡返工（体现业务敏感度）。

**Q35. 同比和环比分别在什么场景下用？本项目怎么用？**

环比（本期/上一期−1）反映短期动量，适合监控周/月经营动作的效果，但受季节性污染严重——本项目双 11 月是淡季的 2.9 倍，11 月环比必涨、12 月环比必降，环比本身不含结论。同比（本期/上年同期−1）剔除季节结构，适合判断趋势与增长质量。本项目两者都产出（`mart_monthly`/`mart_quarterly` 的 mom/yoy 列）：环比用于排班与补货节奏，同比用于经营判断（2021Q4 +84.4%、2022Q2 +69.7%）。两个口径陷阱：① 非完整年度（31 个月）下，2022Q3 仅含 7 月，其季度同比是假象，必须剔除或标注；② 同比要求至少两年同期数据，首年无同比值。这些口径都写进了《指标体系.md》§2。

**Q36. 你为什么用 DuckDB？如果不用会怎样？**

不是为了"用个新技术"，而是把它当成**第二实现**。`etl/warehouse.py` 建了 `dim_member/product/store/date` + `fact_transactions` + `fact_transaction_items` 星型模型，然后用 DuckDB 的窗口函数**重算了一遍 RFM**，与 pandas 版做**逐行一致性断言** —— 实测 35,650 行、5 个字段（recency/frequency/monetary/txn_count/return_amount）零差异，外键零孤儿。

价值在于：pandas 那一版是"业务口径"，SQL 那一版是"独立复算"，两套代码路径完全不同却给出同一个数，才说明口径没漂移。后续任何口径改动，只要两边不再一致，断言立刻报警。不用 DuckDB 也能出数，但就少了这层"自证"。

**Q37. 你怎么保证不同数据源能走同一套 ETL？——后来我把这一层删了，为什么？**

先说原来的设计：`io/schema.py` 定义 canonical 列名 + `SOURCE_MAPPINGS`（synthetic / dunnhumby / uci_retail），`apply_mapping()` 把外部源原始列名改写成 canonical，下游 ETL 一行不改。当时踩过两个真坑（现在仍写在这里，因为**将来真接外部源还会遇到**）：

① **UCI 的 `StockCode` 不是纯数字**（`POST`/`M`/`BANK CHARGES` 是服务码），直接 `astype(int32)` 整列失败 → 映射为**稳定代理 ID**，不丢行、保住跨表引用一致性；
② **`items` 用 `UnitPrice`、`transactions` 用 `Price`**，都指向 canonical 的 `unit_price` → **合并**而非重命名，避免重复列名。

**但 v3.5 我把整套下载器 + 映射层删了。** 为什么？我按"这项能力有没有真实调用链"复核了一遍：

- 三个数据源的 `sha256` **全是 `None`** → 校验分支永远不触发；
- `dunnhumby` / `instacart` **没有 url** → 只能打印下载指引，实际下不了；
- `apply_mapping()` 的**唯一消费方就是下载器自己** —— 主链路 `gen → etl → …` 从不经过它。

也就是说它满足"代码存在 + 单测全绿"，却不满足"被真实数据驱动"。留着的唯一效果是让交付清单多一行 ✅，而面试官只要问一句"这个映射函数在哪个 stage 被调用"就会露馅。**删掉之后 canonical 口径由生成器直接产出，链路更短，也更诚实。** 另外还有一条更本质的理由：项目的核心价值是"合成数据里埋了 8 类先验人群，可以验证聚类找回了多少真实结构"，接英美的第三方数据反而会破坏这个可验证性。

**教训：能力必须有真实调用链，否则是负债。** "我实现了但它没被用到"不是完成度，是技术债。

**Q38. SKU 级关联规则一开始挖出 0 条，你怎么定位的？**

这是个值得讲的排查链。挖掘代码一次跑通（2.5s、内存可控），但规则数是 0。我先排除了"阈值太严"（放宽到 lift>1.2、conf≥0.05 仍是 0），再看全部候选规则：**最高 lift 只有 1.82，confidence 只有 1.1%~3.9%** —— 也就是"买 A 的人里有 3.9% 也买了 B"，毫无业务价值。

根因在**数据生成侧**：锚点只打在品类上（啤酒→纸尿裤），而每个品类有 80+ 个 SKU，同品类内的具体商品是随机采样的。量化验证：同时含啤酒+纸尿裤的交易占 **5.38%**，而独立假设只有 **1.77%**（约 3.0 倍 lift）—— 品类级信号强（这正是品类规则的来源），SKU 级则是被稀释的产物。

修复是给生成器补 SKU 级埋点：每组品类锚点再指定固定 SKU 组合，且每笔命中交易只承载一个 SKU 对（否则挖出来全是 2→2 组合规则，而业务要的是"单品 A → 单品 B"）。结果从 0 条变成 **48 条干净的单品规则，lift 6.8~71.6（中位 46.4）**（v3.2 又补了同品类共购埋点，扩到 48 条）。

**这一条比功能本身更值得记住**：表面是"加一个挖掘层级"，实际卡点在**数据里有没有对应的信号**。如果不追到根因，很容易把"0 条规则"解释成"这个数据集挖不出东西"就收工 —— 那就是一个交付了但没产出的功能。

**Q39. CLV 你是怎么算的？为什么不做 BG/NBD？**

做的是**简化法**并明确标注：`月流失率 = 1-(1-p_90d)^(1/3)`（90 天流失概率折算成月）→ `留存月数 = 1/月流失率` → `CLV = 月均消费 × 留存月数 × 毛利率`。毛利率 0.30 是**假设值**（零售常见 25%~35%），口径和假设都写进了《指标体系.md》§5.5。

没做 BG/NBD 的原因：它需要交易间隔的分布假设和足够长的个体历史，而这个项目的数据窗口只有 31 个月、且是合成的 —— 上了 BG/NBD 也只是把假设藏得更深。简化法的每个输入都能追溯到已有产物、可逐行核对，这对我更诚实。

一个必须处理的边界：流失模型只覆盖末期观察窗内的活跃会员（22,777 / 36,000 = 63.3%），其余会员的 CLV 我用**同客群中位留存月数**兜底，并用 `clv_source` 列标注来源（`model` / `segment_median`），**不静默填 0**。

**Q40. 压测怎么做的？结果说明什么？**

`scripts/exp_scale5.py`：**每个 stage 独立进程**跑（避免同一进程内连跑各 stage 只看到累积峰值），psutil 轮询采样峰值 RSS，逐 stage 记墙钟耗时。scale 5 = 60 万会员 / 525 万交易 / 3,645 万明细，12 个 stage **全部跑通**，合计 12,450s，峰值内存 **7.29 GB**（最高的是 SKU 级规则 one-hot 的 7.29GB，最低的是 RFM 的 1.27GB）。

结论是"8GB 机器能跑完 scale 5，但余量已经很小"，这比"应该能跑"有用得多。

这里还有个教训值得讲：**压测工具自己出过 bug**。第一版没调 `proc.wait()`，`returncode` 恒为 `None`，结果 12 个 stage 里 6 个被标成"失败"（日志显示其实都跑完了）。修好后 ETL 从"失败"变成"9.3s 成功"。**做容量验证时必须先验证压测工具本身是对的** —— 否则结论会完全反过来。

**Q41. 你在这个项目里发现并修过哪些真 bug？**

列三个有代表性的（细节见 `docs/plan/功能实现差距清单.md` §0）：

① **聚类静默丢会员**：`mart_cluster` 35,297 行 vs `mart_rfm` 35,612 行，315 人被丢弃且**没有任何报错**。根因是 `base`（RangeIndex）和 member_id 索引的 Series 做 join 时索引错位。修完加了断言"两表行数必须相等"。

② **KS 指标口径不可比**：我原来的 KS 用的是 `max(累计捕获率 − 累计位置)`，上限被基线率锁死，和业界"KS ≥ 0.30"根本不是一个量。改成标准定义 `max|TPR − FPR|` 后，同一个模型是 **0.492**。

③ **压测脚本自身把成功误判为失败**（见 Q40）。

这三个共同的性质是：**都不报错，只是悄悄给出错误结果**。所以我补了一条导入冒烟测试 + 产物一致性断言，把这类"隐形损坏"挡在 CI 里 —— 这比修 bug 本身更重要。

**Q42. 你怎么保证「说出来的功能都真的实现了」？**

这是我在 v3.3 专门做了一轮核查的问题，也是我认为最值得讲的一条工程纪律。

**背景**：v3.2 收尾时 138 个测试全绿、覆盖率 70.72%、文档里 18 项交付全部标 ✅，看起来可以交付了。
但我意识到一件事：**测试全绿只能证明「代码按我写的执行了」，不能证明「结果是对的」**。

**做法**：逐条把 18 项交付与**真实代码 + 真实产物**三方对上；凡是涉及数值的地方，
**拿两套独立口径算同一个数，再逐行比对**（不是读代码，是复算）。

**结果**：查出 5 个不报错的缺陷 —— 包括一个让 **99.997% 的会员拿到别人的潜力指数**的索引错位 bug、
一个让决策报告同时印出「已达标」与「无一达到 +0.03」的模型口径混用、
一个让门店报表三列整体错位一格的 bug、以及一个让 S1 建议借用 S2 金额的模板 bug。
另外查出 **3 处「交付了但没产出」**（质量报告 HTML 的文件不在仓库里、关联规则网络图没有任何生产代码调用、
画像卡片与差异论证没接进 CLI）和 **11 处文档与实测脱节**。

**我做了什么**：
① 全部修掉，每个缺陷配一条「用第二实现逐行比对」的回归测试；
② 把结论改成**由代码生成**（报告的模型结论段、聚类特征空间对比表都不再写死字符串）；
③ 文档全部回填，并在计划文档里立 §0.9~§0.11 三节留档，不掩盖这段历史。

**关键认知**：其中 3 个缺陷的根因是**索引对齐**（RangeIndex 与 member_id 混用、store_id 与行号混用），另 2 个分别属于**口径混用**与**「本地能跑 ≠ 别人能跑」**。
我在这个项目里同类坑踩了三次，所以现在把它当纪律：**任何 join / reindex 之前先问「两边的索引是一回事吗」**。

这也解释了我为什么引入 DuckDB：**不是为了用新技术，而是为了多一个独立实现来自证 pandas 的结果正确** ——
这 4 个 bug 正是靠「第二实现逐行比对」抓出来的，没有第二实现就没有交叉验证的机会。
